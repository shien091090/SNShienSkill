# 美術經驗

只有美術 agent 讀寫。跨遊戲通用, 不寫單一遊戲的版位、色票或尺寸 — 那些屬該遊戲的 style.md。

**為什麼需要這份**: 美術每次上工都是全新 session, 輸入只有 spec.md, 前幾版的版面判斷與踩過的坑一概不傳承。同一個遊戲改版重做四次, 就有四次機會重犯同一個錯。

兩層:
- **設計理念**(上層): 抽象、跨遊戲的判斷準則。回答的是「兩個設計打架時選哪個、為什麼」, 用來處理沒見過的情況
- **經驗**(下層): `(症狀) → (原因) → (解法)`, 是理念的具體實例。每條尾端標它歸屬的理念編號, 可掛多個

## 怎麼用

**開工(完整實作)**: 先讀理念再讀經驗。style.md 必須有「理念落實」一節, 每條「成立」的理念寫一句本作怎麼落實(例: 「P1: 判定線是全畫面唯一有外暈的元素」)。候選理念不必寫, 也不約束設計。

**處理回饋(美術修正)**: 每條美術回饋動手前先回答「這違反了哪條理念」:
- 答得出來 → 該理念底下補一條經驗(或把回饋加進既有經驗的證據), 並檢查它的「邊界」是不是寫得太寬, 讓這次的錯鑽過去了
- 答不出來 → 寫一條新經驗; 若它和既有某條沒掛理念的經驗是同一個根因, 提一條候選理念

**理念衝突**: 依編號順序, 編號小的優先。P0 固定排頭。

## 理念的寫法與升降

每條理念四欄, 缺一欄就還只是口號:
- **理念**: 一句話, 抽象到換一種遊戲類型也能用
- **犧牲**: 遵守它要付出什麼。寫不出代價的不收
- **證據**: 掛了哪些經驗; 來自老闆回饋的附遊戲名與輪次和原話(原話最能擋抽象化走樣); 來自外部準則的標 `外部: <出處>`
- **邊界**: 什麼情況不適用

**兩個驗收問題**, 升格前必須都答得出來:
1. 想像一個完全不同類型的遊戲(卡牌、平台跳躍、塔防), 這條還能下判斷嗎?
2. 面前有兩個版面, 這條能選出一個嗎? 選不出來就是口號

**狀態**:
- `候選`: 證據只有一條, 或還沒通過驗收問題。不約束設計, 只是提醒
- `成立`: 至少兩條經驗、來自兩個不同情境(不同物件、不同介面區塊或不同遊戲)指向同一根因, 且通過驗收問題
- 另標 `跨遊戲: 已驗證 / 未驗證` — 證據是否來自兩個以上的遊戲。未驗證的成立理念照樣約束設計, 但遇到老闆回饋與它衝突時優先懷疑它

**性質**:
- `可讀性`: 對任何玩家都成立(看不看得清、分不分得出、讀不讀得懂)
- `品味`: 老闆個人的美感偏好。看的人固定是他, 所以一樣跨遊戲有效, 但依 P0 排在所有可讀性理念之後; 不可把品味寫成可讀性的鐵律

**來源**:
- 不標: 從本工作室的回饋與實際修正歸納出來的
- `外部`: 從業界既有準則(例: game-ui-design skill)摘錄、已由老闆逐條篩選過的。外部理念一律從候選起步; **升成立只需一條本工作室的經驗(老闆回饋或實際修正)指向它** — 業界已有廣泛證據, 缺的是「在我們的遊戲與老闆眼裡也成立」這一步。外部證據併進既有理念時只當佐證, 不算升格所需的經驗條數
- 外部準則的原文不在本檔依賴範圍內, 本檔已寫全要用的部分; 不要去翻原 skill 補讀

**降格**: 老闆回饋直接和某條成立理念衝突 → 先縮它的「邊界」; 縮不了就降回候選並寫明衝突的回饋。證據不刪。

**同類合併**: 新理念和既有的只差措辭 → 合併, 證據併過去, 不另開編號。編號不重用。

## 設計理念

### P0 辨識度先於好看
- 狀態: 成立(工作室基準, 不經歸納) / 性質: 可讀性 / 跨遊戲: 已驗證
- 理念: 玩家一眼分得出每種物件與它的狀態(可互動 / 危險 / 已用掉), 才輪到美感
- 犧牲: 裝飾、氛圍、畫面的完整感; 常常得接受較單調或較「工程感」的畫面
- 證據: 本檔所有經驗的共同前提
- 邊界: 只在兩者衝突時才適用; 不衝突時照樣要好看

### P1 視覺權重跟著玩家決策的迫切度走
- 狀態: 成立 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 越接近「玩家此刻要做決定」的資訊越顯眼; 資訊的新舊、演出的華麗程度、系統覺得它多重要, 都不構成加權的理由
- 犧牲: 事件演出(獎勵、升級)不能搶戲, 爽感要從別的地方給(音效、盤面本身的變化), 而不是蓋在決策資訊上
- 證據: 事件提示蓋住常駐資訊、判定線被淹沒、資訊密度逼近上限; 老闆回饋(史萊姆擴張 第 1 輪): 解鎖瞬間側面板「全部疊在一起, 無法辨識」, 事件提示不得覆蓋常駐數值; 外部: game-ui-design(資訊層級裡背景與地形最低調, 不搶戲)
- 邊界: 遊戲暫停或結算畫面沒有即時決策, 這時事後回饋可以升為最高層

### P2 規則上存在的東西, 畫面上就必須存在
- 狀態: 成立 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 會影響結果的規則狀態(歸屬、零效果、隱藏計數)都要有可見的樣子; 玩家看不到的規則, 在他眼裡不是不存在就是 bug
- 犧牲: 畫面元素變多, 必須靠 P1 排層級來撐住密度
- 證據: 零效果事件無聲跳過、整組一起動的格位沒畫歸屬; 外部: game-ui-design(關鍵狀態要隨時一眼可得, 不必暫停或開選單; 可用的操作也要被看見)
- 邊界: 規格刻意要玩家自己推理的資訊(見 P5)不在此列

### P3 一個意義一種長相, 全畫面共用同一本字典
- 狀態: 成立 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 同一個概念在盤面、側欄、提示、結算裡長得一樣; 一種長相也只代表一個意義
- 犧牲: 各區塊不能各自發揮最佳設計, 局部最佳要讓位給全局一致
- 證據: 同概念各區塊用不同顏色、色票與盤面各自畫符號; 外部: game-ui-design(一致性延伸到操作: 同一按鍵、同一按鈕位置永遠同一意義)
- 邊界: 無

### P4 關鍵區分至少走兩條感知通道
- 狀態: 成立 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 玩家必須分清楚的兩件事, 不能只靠一個維度(只有顏色、只有大小)區分; 至少再加一條(形狀、方向、紋理、動態)
- 犧牲: 設計空間變窄, 每新增一種物件都要同時決定兩個維度
- 證據: 「我造成的」與「系統給的」只靠顏色分、三色以上只用顏色編碼; 外部: game-ui-design(色覺異常約佔男性 8%, 紅綠最常撞; 聚焦標示不能只靠變色)
- 邊界: 只用在玩家必須區分的東西; 純裝飾不需要

### P5 畫現況, 不畫未來
- 狀態: 候選(證據一條) / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 美術只呈現已確定的狀態, 不替玩家做規格沒要求的推算
- 犧牲: 放棄一些「看起來很貼心」的輔助
- 證據: 把落點試算畫成現況讀數
- 邊界: 規格明文要求的預測性提示(落點陰影等)照畫

### P6 標籤不能比它描述的東西更顯眼
- 狀態: 候選(證據一條) / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 數字、符號、徽章是附屬在物件上的, 讀完標籤後物件本身的顏色與形狀仍要一眼可辨
- 犧牲: 標籤要縮小、退到角落, 第一眼可能不容易讀
- 證據: 盤面標示置中蓋住格位本身
- 邊界: 物件本身無資訊量時(例如空格上的倒數), 標籤可以是主體

### P7 每個元素都要掙得它的版面
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 上畫面前先問「玩家現在需要它嗎?」, 答不出來就不放, 或改成需要時才出現
- 犧牲: 放棄「資訊齊全」的安心感; 一些好看的裝飾性資訊會被砍
- 證據: 外部: game-ui-design(Every element must earn its screen space、Cluttered HUD)
- 邊界: 規則狀態不因此隱藏(P2 優先); 能砍的是決策用不到的資訊與裝飾

### P8 動態是溝通, 不是裝飾
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 每個動畫都要說得出它在告訴玩家什麼; 動得越多, 每個動作分到的注意力越少
- 犧牲: 待機動畫、呼吸光、背景流動這類「讓畫面活起來」的東西要有理由才留
- 證據: 外部: game-ui-design(Animation is communication, not decoration; Motion guides attention, excess motion kills it)
- 邊界: 盤面上的慶祝演出(爽感)本身就是在溝通「你做到了」, 屬於有理由的動態

### P9 以最混亂的那一刻驗收
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 可讀性以盤面最滿、事件最密集、演出正在播的時候為準, 不以開局的乾淨畫面為準
- 犧牲: 乾淨畫面下可能顯得過度強調(描邊太重、對比太硬)
- 證據: 外部: game-ui-design(Clarity in chaos、Test on the worst target device)
- 邊界: 無

### P10 可讀性不能假設背景固定
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 文字、數字、標示壓在任何可能出現的底色上都要讀得到; 用描邊、陰影、底板至少一種保證, 不靠「這裡剛好是暗的」
- 犧牲: 每段文字多一層處理, 畫面較「硬」
- 證據: 外部: game-ui-design(No Text Outline Or Shadow、Readability Under Motion)
- 邊界: 底色被規格保證永遠不變的區塊(純色側欄)可以只靠對比度

### P11 常駐資訊的位置固定
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 常駐資訊不跟著震動、演出或盤面變化移動; 要動的是遊戲世界, 不是 UI
- 犧牲: UI 無法參與打擊感演出(畫面震動時 UI 不跟著震)
- 證據: 外部: game-ui-design(Stable anchor points、NEVER apply shake to UI, only world)
- 邊界: 盤面尺寸由規則改變(例: 延展)時, 錨在盤面上的標示跟著盤面走, 但側欄與常駐面板不動

### P12 遊戲區優先於 UI
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 玩家視線所在的區域(盤面、落點、正在操作的物件)不壓 UI; 非壓不可就半透明、靠角落、避開操作中的物件
- 犧牲: 事件提示離它描述的東西較遠(與 P19 拉扯, 衝突時 P12 優先)
- 證據: 外部: game-ui-design(HUD Obscures Gameplay、UI Blocking Action)
- 邊界: 遊戲暫停中、需要玩家做選擇的全畫面介面可以蓋住盤面

### P13 事件要排隊, 不能同時冒出來
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 事件提示分優先級、同時可見的數量有上限、高優先可插隊, 其餘依序播
- 犧牲: 低優先事件會延後出現, 與它發生的時點脫鉤
- 證據: 外部: game-ui-design(Notification Queue Management)。與 P1 的「事件提示蓋住常駐資訊」同源 — 同一結算裡連發多個事件時, 就算各自不蓋常駐資訊也會互相疊
- 邊界: 規格明定時序的事件演出(例: 延展呈現時長)照規格, 排隊只管提示層

### P14 頻繁的回饋要合併
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 同類事件短時間內連發, 合併成一個顯示(+50 與 +30 顯示成 +80), 不洗版
- 犧牲: 失去每一筆的個別回饋
- 證據: 外部: game-ui-design(Notification 合併、Damage Number 群聚, 同時可見 5~6 個為上限)
- 邊界: 只合併同類; 不同類事件合併會違反 P3

### P15 回饋的視覺強度和事件的份量成正比
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 大事件大、小事件小, 分級要一眼可辨; 每個事件都用最強演出等於沒有分級
- 犧牲: 小事件的回饋要刻意做得樸素
- 證據: 外部: game-ui-design(Damage Number 依類型差異化, 爆擊 150% 大小加震動)
- 邊界: 無

### P16 有狀態的物件, 每個狀態都要有獨立外觀, 包括過渡狀態
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 列出物件的全部狀態(未就緒 / 快達成 / 就緒 / 使用中 / 停用)逐一設計; 「快達成了」要有預告, 不要從未就緒直接跳到就緒
- 犧牲: 每個物件的設計工作量變多
- 證據: 外部: game-ui-design(Cooldown Indicator 的五種狀態)
- 邊界: 無

### P17 進度類資訊, 圖形給趨勢、數字給精確
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 進度同時用圖形(條、扇形)與數字表達; 達成的瞬間要有獨立的回饋
- 犧牲: 佔用較多版面
- 證據: 外部: game-ui-design(Cooldown「Combined (best)」)
- 邊界: 版面極度受限時保留數字, 圖形可省

### P18 重要資訊不能只存在一瞬間
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 閃過就消失的重要內容(獲得了什麼、改變了什麼), 要能在別處查到(常駐欄或結算畫面)
- 犧牲: 常駐欄或結算畫面要多留位置
- 證據: 外部: game-ui-design(Notification History access、Never lose important info)
- 邊界: 純爽感、不含資訊的演出不需要留存

### P19 資訊盡量貼著它描述的物件
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 描述某物件的資訊放在該物件旁邊, 讓玩家不必把視線移到別處再對回來
- 犧牲: 盤面上的元素變多(受 P6、P12 約束)
- 證據: 外部: game-ui-design(Diegetic UI)
- 邊界: 需要頻繁查看或互相比較的資訊放固定位置; 與 P12 衝突時 P12 優先

### P20 資訊分層, 細節等玩家要時才展開
- 狀態: 候選 / 來源: 外部 / 性質: 可讀性 / 跨遊戲: 未驗證
- 理念: 一眼層只放決策必要的; 次一層在滑鼠停留或選取時出現; 完整細節要玩家主動打開
- 犧牲: 細節不再一眼可見, 需要多一個動作
- 證據: 外部: game-ui-design(Progressive Information Disclosure)
- 邊界: 規則狀態不可藏到第二層以下(P2 優先)

## 經驗

### 版面 / 遮擋

- 事件提示(延展、重抽、獎勵、連鎖)蓋住常駐資訊(進度數字、色票、進度條) → 事件層與常駐層共用同一塊版位, 只靠時間錯開 → 常駐資訊有專屬矩形, 事件提示一律排在其外; 真的要疊時只疊在該側的空白區, 不疊在任何數值上〔P1〕
- 盤面上的標示(數字、符號)蓋住它所描述的物件本身 → 標示置中在格位上 → 錨在格角並縮到格位的 1/4 以內, 讓被描述的顏色/形狀維持可讀〔P6〕

### 視覺層級

- 規則上的關鍵判定線(中線、安全線、分界)被其他元素淹沒 → 所有元素同一個權重 → 判定線的層級最高: 畫在所有盤面內容之後, 給它描邊或外暈保證任何底色上都讀得到, 並且不隨遊戲階段淡出〔P1〕
- 資訊密度逼近上限(同時有數字、符號、輔助線、狀態標示) → 每加一個元素就加一種顏色或一種亮度 → 先排層級再配色: 判定線 > 玩家當下要決策的資訊 > 常駐狀態 > 事後回饋; 同層級才比大小與顏色〔P1〕

### 語意一致

- 同一個概念在不同地方用不同顏色或形狀 → 各區塊各自設計 → 建立全局語意色(例如左/右、敵/我、安全/危險), 盤面、側欄、結算標籤、提示全部共用同一套〔P3〕
- 兩種語意不同的事件看起來一樣, 玩家分不出「我造成的」與「系統給的」 → 只有顏色不同 → 形狀語言也要不同(方角 vs 圓角 vs 六角、外擴 vs 內收、箭頭方向相反)〔P4〕

### 狀態可辨識

- 「什麼都沒發生」與「機制壞掉」分不出來 → 零效果的事件無聲跳過 → 零效果也要有可單獨辨識的回饋, 且與有效果的版本形狀不同〔P2〕
- 一組格位「屬於同一個整體」讀不出來, 玩家誤以為是各自獨立 → 只標個別格位 → 用連接桿、共同輪廓、共用紋理或編號徽章表達歸屬; 只要規則上會「整組一起動」, 歸屬就必須畫出來〔P2〕

### 無障礙

- 只靠色相區分的物件, 色弱玩家分不出 → 三色以上只用顏色編碼 → 每個顏色配一個幾何符號(圓/方/三角/菱), 色票、預覽、落點預示、盤面格全部共用同一套符號〔P4〕〔P3〕

### 與規格的分界

- 規格說「不做預測性提示」, 美術卻畫出了預測 → 把「現況讀數」與「落點試算」混為一談 → 判準: 輸入只有已鎖定/已確定的狀態才是現況讀數, 任何把玩家當前操作中的物件算進去的都是預測, 不畫〔P5〕

### 外部準則(game-ui-design 摘錄, 經老闆篩選)

- 操作存在但玩家不知道 → 按鍵只寫在說明文件或不寫 → 可用的操作與對應按鍵顯示在畫面上; 可互動的元素在滑鼠停留時要有外觀變化〔P2〕
- 同一個按鍵或按鈕位置在不同畫面意義不同, 玩家誤按 → 各畫面各自設計 → 確認、取消、返回的位置與按鍵全遊戲固定〔P3〕
- 聚焦或選取狀態色弱看不出來 → 只靠變色表示 → 加外框、外暈或放大, 且在任何底色上都看得到〔P4〕〔P10〕
- 等級、強度、稀有度只能靠顏色認 → 用色相編碼等級 → 用可數的疊加元素表示(無框 / 單框 / 雙框 / 加角飾)〔P4〕
- 文字在某些底色上讀不到 → 對比不足或字重太細 → 對比度至少 4.5:1, 字越小對比要越高; 不用細字重〔P10〕
- 字太小一眼讀不出 → 以設計當下的螢幕判斷 → 字級下限換算成畫布高的比例: 最小約 1/77, 關鍵數字約 1/45(原文 1080p 下 14px / 24px)〔P0〕〔P9〕
- 色弱玩家分不出兩種顏色 → 兩色色相不同但明度相近 → 轉灰階測試, 各色仍要分得開; 紅綠是最常撞的一組〔P4〕
- 關鍵提示出現太慢或消失太突然 → 進退場用同一種節奏 → 關鍵資訊出現即時, 消失要緩(淡出約 500ms)〔P13〕〔P18〕
- 誰疊在誰上面每次臨場決定, 改版後層級錯亂 → 沒有明文的繪製順序 → style.md 列一張繪製層級表; 間距用固定級距(如 8/16/24/32)〔P1〕〔P3〕
- 不可逆的操作被誤觸 → 與一般操作同樣的手續與外觀 → 多一道手續(長按或確認), 外觀與相鄰按鈕不同; 長按要畫出進度〔P2〕
