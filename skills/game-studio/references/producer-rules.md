# 製作人守則

老闆立的跨遊戲規則, 製作人每次開場讀。**只有老闆能新增或修改**; 製作人可以提議, 但要他點頭才寫進來。agent 不讀這份 — 守則要傳到 agent 手上, 一律由製作人寫進它們清單上的檔案(decisions.md、spec.md、prompt)。

每條四欄: 規則 / 為什麼 / 生效狀態 / 各狀態怎麼做。各狀態參考檔只寫一句「執行守則中標記本狀態的條目」, 具體做法以本檔為準。

## R1 只能有一套操作

- **規則**: 一款遊戲要嘛只用滑鼠玩, 要嘛只用鍵盤玩, 不可同時有兩套操作。遊戲內所有動作(含暫停、重開、放棄、事件中的選擇、說明翻頁)都用同一種輸入完成
- **為什麼**: 兩套並存時, 玩家不知道該用哪套, 規格與實作也要多處理一套仲裁
- **生效狀態**:
  - concept: 拍板時在 decisions.md「確定要有的」寫「操作: 只用 <滑鼠|鍵盤>」, 另一種寫進「明確不做的」。選哪種是設計決策, 你定, 理由寫一句
  - spec-draft / spec-review: 規格「操作」章節只能出現一種輸入。檢查每個玩家動作都有該輸入的對應(滑鼠版的暫停要有畫面按鈕、鍵盤版的選擇要有按鍵)
  - build: 讀碼時確認 game.js 沒有掛另一種輸入的事件監聽。有 → 當 bug 退 RD
- **已在迭代中的遊戲**: 本條生效前做的版本若兩套並存, 下一次進 spec-draft 時在 decisions.md 裁定保留哪一種, 修訂紀錄寫明是依守則 R1

## R2 每個版本都附玩家說明

- **規則**: 每個交給老闆試玩的版本, 都要有一份給玩家看的遊戲說明, 在遊戲內呈現。精簡、以圖為主, 一頁放不下就分頁
- **為什麼**: 規格是給團隊看的, 玩家不會讀。說明寫得出來多短, 也是規則複雜度的訊號
- **原則**: 寫法照 `references/guide-principles.md`, **不給模板** — 每款遊戲的玩法不同, 呈現方式由企劃依原則自己決定
- **生效狀態**:
  - spec-draft: 企劃寫完 spec.md 後同一個 session 另交 `guide.md`
  - spec-review: 審查企劃多審一項: 說明與規格是否一致、玩家會操作到的動作有沒有漏
  - build: 美術畫說明頁的示意圖, RD 做說明畫面(開場顯示、可翻頁、遊戲中可再叫出)。你核對說明畫面存在、翻頁只用 R1 選定的輸入
  - playtest: 說明與遊戲實際行為不符 → 當 bug
