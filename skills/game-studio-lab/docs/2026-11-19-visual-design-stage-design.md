# game-studio-lab 視覺設計階段設計

日期: 2026-11-19

## 目的

打磨時美術方向常在試玩後才被推翻, 要整輪重做(例: 2026-11-19 三款開始畫面先做成玩法示範, 使用者看了才說要的是主視覺小動畫, 多跑了一輪打磨)。在深掘與打磨之間加一個**視覺設計階段**, 先把核心視覺元素的方向定下來, 打磨照著做, 少走冤枉路。

成功的樣子: 深掘結束選「下一階段」後, 使用者先看到一份核心視覺元素清單(文字)確認或增刪; 接著打開一頁 Artifact, 每個元素並排幾個方案, 靜態的直接看圖、動態與特效按播放鍵看效果; 回報每項挑哪個, 流程進打磨, 打磨第一輪做出來的遊戲就是挑中的樣子。

## 範圍

要做:
- 新階段 `visual`(視覺設計), 兩個停點: 確認元素清單、挑方案
- 深掘選 `next` 改進視覺設計(原本直接進打磨)。**每個專案只跑一次**: 打磨停點不加回視覺設計的選擇, 打磨之後一律接下一輪打磨(使用者決定)
- 底版在視覺設計就定: 列清單時一起挑出要進打磨的那一款, 打磨第一輪直接用它, 不再自己挑
- 方案頁(本機 HTML, 主 session 發布成 Artifact)
- 挑選結果寫成「視覺方向」, 打磨的設計與美術照著做

不做:
- 非 lab 專案(例 Bubble Tempo)的入口: 之後真的要用再加
- 已經在打磨的專案(接力吉尼、魂匠守衛者)補跑視覺設計: 只跑一次的原則下不提供
- 音效方向(只管看得到的東西)
- 發布素材(圖示、橫幅、主色): 發布階段已有自己的挑選

反目標(做了也算失敗):
- 方案只是同一個東西換顏色: 每個元素的方案要是**不同方向**(構圖、動態節奏、造型語言不同)
- 方案畫得跟遊戲裡實際能做出來的不一樣(例: 用遊戲沒有的濾鏡或外部圖): 方案一律用遊戲美術同一套畫布程式畫, 挑中的才能直接接進遊戲

## 做法比較

| 做法 | 取捨 |
|---|---|
| **A. 流程內正式階段(採用)** | 每款都走同一套、可中斷接續、挑選有紀錄; 要改流程程式與測試 |
| B. 主 session 臨時做 | 很快能用, 但每次做法不一、沒停點紀錄 |
| C. 塞進打磨第一輪設計 | 改動最小, 但打磨中途卡住等挑, 第二輪以後用不到 |

使用者選 A, 因為目的是「每款進打磨前都有固定這一步」。

## 流程

```
深掘 --next--> 檢討假設 --> 視覺設計 ---------------------------------> 打磨第 1 輪
                 1. 挑底版 + 列清單(設計節點)
                 2. 停點① waiting_visual_list: 使用者確認底版與清單(可增刪)
                 3. 出方案(美術節點, 每個元素一次, 依序跑)
                 4. 組方案頁(程式)
                 5. 停點② waiting_visual_pick: 主 session 發 Artifact, 使用者挑
                    - redo: 只重做指定元素(帶意見), 回到 3
                 6. 寫視覺方向(程式)
```

- 深掘選 `next` 照舊先跑檢討假設(深掘最後一輪的回饋照常整理), 之後才進視覺設計; 視覺設計本身不跑檢討假設、不做試玩, 不算一輪探索 / 深掘 / 打磨
- 底版: 設計節點讀深掘最後一輪的回饋與 `hypotheses.md` 挑出要打磨的那一款(就是現在打磨第一輪設計挑底版的判斷, 提前做), 寫進 `elements.md` 開頭的 `底版: <深掘資料夾>/<款>`; 停點①由使用者確認, 可改。方案頁載入這款的 `art.js`, 方案程式呼叫它的畫法
- 定完方向進打磨第一輪: 打磨設計**照 `elements.md` 的底版**複製進 `polish/`(不再自己挑), 再依視覺方向改
- 只跑一次: 進入打磨後不會再回到視覺設計; 退回深掘 / 探索(back-*)後再選 next 也不再跑(已有 `visual/direction.md` 就直接進打磨)。使用者想換方向時在打磨訪談的回饋裡講, 由打磨照一般回饋處理

## 資料夾與檔案

全放 `<專案>/visual/`(固定一個資料夾, 再跑一次覆蓋; git 留歷史):

| 檔案 | 誰寫 | 內容 |
|---|---|---|
| `elements.md` | 設計節點寫, 主 session 依使用者意見改 | 元素清單(格式見下) |
| `options/<元素代號>-<A/B/C>.js` | 美術節點 | 一個方案, 格式見下 |
| `options/<元素代號>.md` | 美術節點 | 每個方案一句說明(方向差在哪) |
| `options/index.html` | 程式 | 方案頁, 單檔內嵌所有方案程式與遊戲的 `art.js` |
| `pick.md` | 主 session | 使用者的選擇(格式見下) |
| `direction.md` | 程式 | 定案的視覺方向: 每個元素選了哪個方案、說明、使用者附註、方案程式路徑 |

`elements.md` 格式(每個元素一節):

```
## title — 開始畫面
類型: 動態            (靜態 / 動態)
內容: 以主視覺呈現的小動畫, 底下「按任意按鍵開始遊戲」
為什麼是核心: 玩家第一眼看到的畫面
```

元素代號用英文小寫(檔名用)。清單的來源與方向:
- 固定類: 開始畫面、主角、介面風格(HUD、按鈕、字)
- 依玩法類: 和核心玩法綁在一起的動態, 讀 spec.md 與 hypotheses.md 中成立的「機制 → 體驗」找出來(例: Bubble Tempo 的泡泡隨拍呼吸、踩中拍點的效果; 接力吉尼的跳躍、觸發機關)
- 元素數量由設計依遊戲決定, 不設固定數; 太多(例如超過 8 個)時設計要合併或排優先順序, 在回報寫明

## 方案格式

每個方案是一個 JS 檔, 只定義一個物件, 用遊戲 `art.js` 匯出的畫法(方案頁會先載入底版遊戲的 `art.js`):

```js
window.VISUAL_OPTION = {
  element: "title", id: "A", kind: "anim",   // "static" | "anim"
  size: [1280, 720],                          // 畫布尺寸, 依元素取景(主角可用 400×400)
  duration: 4,                                // 動態一次播放秒數; 循環的寫一圈長度
  loop: true,
  draw(ctx, t) { /* t = 秒; 靜態忽略 t */ }
};
```

- 每個元素出 3 個方案(A/B/C), 方向要明顯不同(反目標見上)
- 方案程式在 `draw` 裡可以呼叫 `Art.xxx` 或自己畫; 新增的畫法寫在方案檔裡, 不改遊戲的 `art.js`
- 美術節點每個元素起一次 `claude -p`, **依序跑**(並行容易吃光記憶體, 2026-11-19 兩個流程並行被系統砍過); 每完成一個元素寫完成標記, 中斷接續時跳過已完成的

## 方案頁

程式把 `art.js` 與所有方案檔內嵌成一個 HTML(Artifact 是單頁, 不靠相對路徑):
- 每個元素一節: 標題、為什麼是核心、3 個方案並排(手機寬度改直排), 每個方案標代號與一句說明
- 靜態方案: 直接畫一次
- 動態方案: 每個畫布下有播放 / 暫停鍵與進度條, 預設停在第 0 秒的畫面; 循環的播完接著循環; 同時只播一個不強制
- 畫布等比縮進欄寬, 不裁切

主 session 用 Artifact 發布 `options/index.html`(單檔, 不必帶 files), 把連結給使用者; redo 後用同一個檔路徑再發布, 網址不變。挑完不刪 Artifact(使用者要刪再刪)。

## 停點與 CLI

| 停點 | 狀態 JSON | 可選 | 回饋檔 |
|---|---|---|---|
| ① 清單 | `waiting_visual_list`, 帶 `elements` 路徑 | `confirm` | 不帶(主 session 直接改 `elements.md`) |
| ② 挑方案 | `waiting_visual_pick`, 帶 `options_page` | `pick` / `redo` | `pick.md` |

`pick.md` 格式:

```
title: B
hero: A
beat-hit: C, 光圈再大一點
```

- 每行「元素代號: 方案代號[, 附註]」; 每個元素都要有一行, 缺了 CLI 擋下
- `redo` 用同格式只列要重做的元素, 附註寫意見(例「beat-hit: 都太花, 要更簡潔」), 只重做這些, 其他保留
- 附註進 `direction.md`, 打磨照著調

`confirm` 時程式檢查 `elements.md` 每節有代號、類型、內容; 不合格擋下並說哪節缺什麼。

## 打磨怎麼用視覺方向

- `prompts/design-polish.md`: 有 `visual/direction.md` 時, 規格的開始畫面、主角、介面、核心動態照方向寫, 並列「視覺方向對照」一節(每個元素寫在哪一節)
- `prompts/art.md`(打磨): 照方向做; 挑中的方案程式是**起點**, 搬進 `art.js` 改成遊戲用的函式(座標、參數接遊戲狀態), 不是另外重畫
- 方向檔在打磨期間不變; 打磨中的視覺意見走一般回饋

## 其他

- 視覺設計的 commit: 停點① `[docs] [<專案>] 視覺設計列出核心視覺元素`; 停點② `[feat] [<專案>] 視覺設計產出方案`; 寫完方向 `[docs] [<專案>] 視覺設計定案方向`(CLI 依停點自動產生, 同現有做法)
- 經驗收件匣照舊: 美術節點的經驗提案寫進收件匣
- SKILL.md 加「視覺設計」段: 兩個停點主 session 要做什麼(停點①把清單用白話列給使用者、依回覆改檔; 停點②發 Artifact、把回覆寫成 pick.md)
- 既有專案: 停在打磨的專案不受影響(停點選項不變, 已存的進度照舊接得上)
