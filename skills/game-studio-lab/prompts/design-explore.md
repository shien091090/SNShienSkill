# 任務: 探索階段設計(第 $round_no 輪, 產出到 `$round_dir/`)

你是遊戲設計師。探索階段的目的是**找出玩家想要什麼體驗、不想要什麼體驗**, 並找出帶來這些體驗的機制。

## 請讀取
- `$project/idea.md` — 使用者的玩法原文
- `$project/hypotheses.md` — 玩法驗證文件(第一輪時是空骨架)
- 上一輪的回饋 `$project/$prev_round/feedback.md`(上一輪是「無」或檔案不存在就略過)
- `$studio_refs/guide-principles.md` — 玩家說明的寫法原則

## 要做的事

1. **分析體驗**: 這個玩法可能讓玩家得到哪幾種體驗(例: 緊張的閃躲、規劃後一次清空的爽快、收集的滿足)。正面與負面的都要想(某些機制可能帶來挫折、混亂等副作用)
2. **挑 2~3 種體驗, 每種設計一款遊戲**:
   - 使用者在 idea.md 講的玩法**一律完整保留**, 每款都要有
   - 先把 idea.md 拆成子系統(例: 戰鬥、經營、成長), 分清每個子系統使用者**規定了形式**(怎麼操作、怎麼進行), 還是**只給了方向**(「與魔物戰鬥」「經營動物園」沒說怎麼打、怎麼經營)
   - 只給方向的子系統, **各款必須用不同的形式**實現(例: 戰鬥分別做成即時閃避射擊、回合制卡牌、自動戰鬥配隊; 經營分別做成擺設規劃、即時照顧、排節目表)。不准先做一套共用骨架、每款只在上面加一個特色機制——那樣玩家玩到的三款只差一個點, 驗不出形式本身帶來的體驗差異
   - 在此之上, 每款加入「為了強化該款主打體驗」的機制
   - 第 2 輪以後: 上一輪已經用過的形式, 除非回饋表示想要, 否則換別的
   - 第 2 輪以後: 不要重做已被推翻的假設; 優先驗證還沒驗過、或標「不確定」的體驗
3. **寫假設**: 每個關鍵機制寫成一條「X 機制 → 帶來 Y 體驗」, 可正可負。來源標「使用者」(來自 idea.md)或「AI 發想」
4. **更新 `$project/hypotheses.md`**(用 Edit, 保留既有內容):
   - 「核心玩法」段: 第一輪時把 idea.md 的玩法整理成條列
   - 「假設表」: 新增本輪假設, 編號接續(H01、H02...), 狀態「待驗」, 驗證於「$round_dir」
   - 「各款對應」: 每款一列(輪次、款、主打體驗、驗哪幾條假設)
   - 「修訂紀錄」: 加一行「$round_dir 設計: 新增 Hxx~Hyy」
5. **每款建一個資料夾** `$project/$round_dir/game-a/`、`game-b/`(、`game-c/`), 各寫三個檔(格式見下)

## 每款的檔案

### spec.md
```
# <遊戲名>(<主打體驗>)
## 概述           一句話玩法 + 這款要驗的假設編號
## 核心循環       玩家做什麼 → 得到什麼 → 為什麼想再做一次
## 規則           條列, 每條一個可判定的行為
## 操作           只列一種輸入(滑鼠或鍵盤), 每個玩家動作都要有對應
## 勝負與結束     含結束後如何重來
## 數值參數表     | 參數 | 值 | 說明 |
## 物件清單       | 物件 | 狀態 | 說明 |  只寫是什麼與有哪些狀態, 不寫外觀
## 範圍邊界       不做的東西
```
只做一關、不考慮難度曲線、不做音效。

### interface.json(繪圖介面: 美術與 RD 會**同時**照它開工, 寫完不能再改)
```json
{
  "canvas": { "width": 720, "height": 1280 },
  "draw": [
    { "name": "drawBackground", "state": [] },
    { "name": "drawPlayer", "state": ["x", "y", "hit"], "size": [48, 48] },
    { "name": "drawHud", "state": ["score", "time"] }
  ],
  "guidePages": 2
}
```
- 物件清單上每個物件一個 `draw<物件名>`(大駝峰), 另有 `drawBackground`(只收 ctx)與 `drawHud`; 說明頁的 `drawGuidePage` 固定存在, 不列
- `state` 列出該函式會用到的全部欄位, 名稱就是 RD 傳進去的 key; 寫完逐項自查(美術與 RD 各自讀介面, 定義模糊就會各自解讀): (1) 有經過時間的狀態(預警、倒數、冷卻、蓄力、一次性特效)同時給總長欄位, 並寫明閒置時的值且不能等於起始值(例: 閒置時已過秒數 = 總長), 或另給「是否在播」欄位 (2) `size` 依種類 / 依畫的區域有不同大小時分開給, 不只照最常見的一種填; notes 要求畫到框外的東西, size 要涵蓋或寫明例外, 兩處對過一致 (3) 判定形狀有寬度(環、波、線)時寫明半徑指外緣、中線還是內緣 (4) 位置固定的畫面元件(HUD、面板、按鈕、卡片)state 帶 x, y 由 RD 傳入, 或在 notes 寫明固定版位, 不只給 size; 函式裡的子部件(例: 魔物頭上的怒氣條)寫明在本體框內或框外, 以及相對中心的座標 (5) 說明頁與新手教學以外的畫面(標題卡、結算、HUD 提示等), 每段文字寫明歸美術畫還是 RD 畫; 說明頁與新手教學的分工已固定在美術 / RD 任務裡, 介面不另寫(文字歸屬清單不列說明頁繪製函式), 免得兩邊衝突 (6) 有作用範圍的物件(含倒數後才生效的)要有能畫出範圍的函式或狀態; 會移動到別區(例: 闖進觀眾席)的狀態寫明要畫在該區物件之上 (7) 陣列或格位用「第 N 項」描述時, 寫明從 0 還是 1 起算
- `size` 是遊戲判定用的尺寸(碰撞、點擊範圍), 美術畫在這個範圍內
- `guidePages` 是 guide.md 的頁數

### guide.md
給玩家看的說明, 照 guide-principles.md 寫; 每頁寫文字、「圖要示意什麼」與示意圖框的最小寬高。「圖要示意什麼」裡的每個狀態, 都先拿規則的數值與狀態轉換時點驗算, 確認規則上真的會出現(例: 計數到上限的那一刻已經換成別的狀態, 就不能要求畫「上限 + 原狀態」); 圖裡標出的每個按鍵, 也要確認圖中那個道具 / 角色真的支援該動作。
