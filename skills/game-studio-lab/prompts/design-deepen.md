# 任務: 深掘階段設計(第 $round_no 輪, 產出到 `$round_dir/`)

你是遊戲設計師。深掘階段已經知道玩家要什麼體驗, 目的是**用不同的機制把目標體驗做得更強、把不要的體驗避得更乾淨**。

## 請讀取
- `$project/idea.md` — 使用者的玩法原文
- `$project/hypotheses.md` — 玩法驗證文件; 「已確認的體驗」「機制清單: 保留 / 避開」是本階段的前提
- 上一輪的回饋 `$project/$prev_round/feedback.md`
- 上一輪各款的 spec.md(`$project/$prev_round/*/spec.md`), 了解已經做過什麼
- `$studio_refs/guide-principles.md`

## 要做的事

1. 從驗證文件確認: 目標體驗(想要)、要避開的體驗(不要)、必留機制、必避機制
2. **設計 2~3 款**: 每款都包含 idea.md 的玩法與全部「保留」機制, 一律不碰「避開」機制。款與款之間的差別是**用不同的新機制去強化同一種目標體驗**(或更徹底地避開不要的體驗)
   - 「保留」的是機制本身, 不是上一輪某款的實作細節。使用者(idea.md 或回饋)只給概念、沒給形式的子系統(例: 「布置機關」沒說有哪些機關、怎麼作用), **各款必須用不同的形式**實現: 物件種類、觸發方式、作用對象都不同(例: 一款是被技能打中才觸發的連動裝置, 一款是改變路線的擋板與傳送門, 一款是指定魔物行動的節目卡)。不准三款共用同一組基礎物件、只在上面加一個特色機制——使用者會覺得三款一樣
   - 場上會自己行動的角色(例: 玩家不操作時的魔物), 每種都要有會讓牠主動和其他物件相遇的移動方式, 不准有原地不動或只在特定條件才動的種類
   - 寫完自查: 用隨手的擺法(不是最佳解)照規則在腦中跑一遍, 確認這款主打的事件(連鎖、表演、收益)會自然而頻繁地發生; 只有精準擺位才會發生、其餘時間玩家只能空等的話, 改規則(加大作用範圍、讓角色主動移動、加觸發來源)
3. 新機制各寫成假設「X 機制 → 強化 Y 體驗」, 來源標「AI 發想」; 也可以重新驗證標「不確定」的舊假設
4. 更新 `$project/hypotheses.md`(用 Edit): 假設表新增(編號接續, 狀態待驗, 驗證於 $round_dir)、各款對應、修訂紀錄
5. 每款建 `$project/$round_dir/game-a/` 等資料夾, 寫 spec.md、interface.json、guide.md

### spec.md
```
# <遊戲名>(<這款的新機制>)
## 概述 / 核心循環 / 規則 / 操作(只一種輸入)/ 勝負與結束 / 數值參數表 / 物件清單 / 範圍邊界
```
只做一關、不考慮難度、不做音效。

### interface.json
`{"canvas": {...}, "draw": [{"name", "state", "size"}...], "guidePages": N}` — 物件清單每個物件一個 `draw<物件名>`, 另有 `drawBackground`(只收 ctx)與 `drawHud`; `drawGuidePage` 固定存在不列。寫完逐項自查(美術與 RD 各自讀介面, 定義模糊就會各自解讀): (1) 有經過時間的狀態(預警、倒數、冷卻、蓄力、一次性特效)同時給總長欄位, 並寫明閒置時的值且不能等於起始值(例: 閒置時已過秒數 = 總長), 或另給「是否在播」欄位 (2) `size` 依種類 / 依畫的區域有不同大小時分開給, 不只照最常見的一種填; notes 要求畫到框外的東西, size 要涵蓋或寫明例外, 兩處對過一致 (3) 判定形狀有寬度(環、波、線)時寫明半徑指外緣、中線還是內緣 (4) 位置固定的畫面元件(HUD、面板、按鈕、卡片)state 帶 x, y 由 RD 傳入, 或在 notes 寫明固定版位, 不只給 size; 函式裡的子部件(例: 魔物頭上的怒氣條)寫明在本體框內或框外, 以及相對中心的座標 (5) 說明頁與新手教學以外的畫面(標題卡、結算、HUD 提示等), 每段文字寫明歸美術畫還是 RD 畫; 說明頁與新手教學的分工已固定在美術 / RD 任務裡, 介面不另寫(文字歸屬清單不列說明頁繪製函式), 免得兩邊衝突 (6) 有作用範圍的物件(含倒數後才生效的)要有能畫出範圍的函式或狀態; 會移動到別區(例: 闖進觀眾席)的狀態寫明要畫在該區物件之上 (7) 陣列或格位用「第 N 項」描述時, 寫明從 0 還是 1 起算。美術與 RD 會同時照它開工, 寫完不能改。

### guide.md
照 guide-principles.md, 每頁寫文字、「圖要示意什麼」與示意圖框的最小寬高。「圖要示意什麼」裡的每個狀態, 都先拿規則的數值與狀態轉換時點驗算, 確認規則上真的會出現(例: 計數到上限的那一刻已經換成別的狀態, 就不能要求畫「上限 + 原狀態」); 圖裡標出的每個按鍵, 也要確認圖中那個道具 / 角色真的支援該動作。
