# 音效經驗

只有音效 agent 讀寫。跨遊戲通用, 不寫單一遊戲的素材檔名、音量或事件表 — 那些屬該遊戲的 sound.md。

**為什麼需要這份**: 音效每次上工都是全新 session, 前幾版找過哪些素材站、哪種授權踩過雷、哪種聲音被老闆嫌吵, 一概不傳承。

## 怎麼用

- **開工**: 先讀完本檔。sound.md 的「理念或經驗落實」一節, 寫本檔裡跟本作有關的條目怎麼落實
- **處理回饋(音效修正)**: 每條音效回饋動手前先判定它屬於下面哪一類, 修完後依「怎麼長」回寫

## 怎麼長

- 格式: `(症狀) → (原因) → (解法)`, 附遊戲名與輪次; 來自老闆回饋的附原話
- **必須隔一次實際修正才寫**: 老闆的音效回饋先進該遊戲的 feedback, 走過一次音效修正、真的改過之後, 才把通則寫進來。只聽到一次回饋就寫, 會把「這一輪的個人偏好」誤寫成通則
- 標性質: `辨識`(任何玩家都成立: 聽不聽得出是哪個事件、會不會蓋掉重要的聲音)或 `品味`(老闆個人偏好: 好不好聽、風格)。兩者不混, 品味條目遇到新遊戲時只當參考
- 同一個根因累積到兩條以上、且來自不同事件或不同遊戲時, 可以在本檔最上方提一條「原則」(寫明犧牲與邊界), 形式比照美術經驗的設計理念

## 素材來源

- `品味` **程式合成的背景音樂被嫌「太快、一直重複很膩」** → 為了拍速與循環點精準而自己合成, 結果只有 8 小節(12.8 秒)一個循環, 一關聽好幾十輪, 加上 150 BPM 偏快 → 背景音樂優先找現成整首曲子截段, 一關的循環至少幾十小節; 合成只當最後手段。(BubbleCatcher round-7, 老闆原話「現在 BPM 太快、節奏一直重複聽得很膩, 希望換比較好聽的音樂」; 換成三首現成曲, 效果待試玩)
- `辨識` **需要精準 BPM 與整數小節循環的背景音樂找不到可驗證的** → CC0 音樂站多半沒標 BPM 或只有短循環(OpenGameArt), FreePD 已在 2025 年關站, Pixabay 對下載工具回 403 → incompetech(Kevin MacLeod, CC BY 4.0, 免登入)有一份 `https://incompetech.com/music/royalty-free/pieces.json` 列出每首曲名、BPM、長度、風格, 先用它篩拍速與長度, 再下載候選實測; 他用編曲軟體做的電子 / 流行曲量起來 BPM 跟標示一致到 ±0.01, 漂移幾乎為 0(真人演奏的曲子殘差會到 10 毫秒以上, 要排除)。代價是要署名。(BubbleCatcher round-7 後的 build)
- `辨識` **背景音樂節奏感太弱、抓不到拍子** → 選曲只驗了 BPM 準度與漂移, 沒驗「拍點上的大鼓有沒有壓過其他聲部」: 工業電子曲的失真低頻在反拍、十六分位置一樣在敲(35~110 Hz 起音上升量拍上 27 dB、反拍 21 dB), 48 小節裡只有 6 小節四拍都清楚, 還夾一段 4 小節弱鼓間奏 → 候選曲先量「大鼓清楚度」: 35~110 Hz 帶通、5 毫秒包絡, 每拍的起音上升量減去同拍反拍與兩個十六分位置的最大上升量, 要求每小節四拍都 ≥ 3 dB; 再逐小節掃整首, 截取窗避開無鼓的過門與 breakdown。曲庫風格欄標 Driving、樂器只有 Synths + Percussion 的四拍電子舞曲最容易過(換上的曲子清楚度中位 35 dB、47/48 小節四拍都清楚)。只看 BPM 擬合分數或拍上起音量會被騙: 舊曲這兩項都不差。(BubbleCatcher round-8, 老闆原話「第三首歌的節奏感太弱, 很難抓到拍子在哪」; 換曲, 效果待試玩)

- `辨識` **低拍速(約 95~105 BPM)又要每拍大鼓的曲子幾乎找不到** → 四拍大鼓是 House / 迪斯可 / EDM 的手法, 這些曲風多在 115 BPM 以上; 100 BPM 左右的曲子多是一、三拍大鼓、二、四拍小鼓的流行與放克, 量出來四拍都清楚的小節近乎 0。incompetech 該區間約 80 首有鼓的曲子只有 2 首過 → 三招擴大候選: (1) incompetech 曲庫的 BPM 欄有些標成兩倍(例: 實際 105 標 210、實際 100 標 200), 篩選時連兩倍區間一起列入, 量的時候用標示值的一半; (2) OpenGameArt 用進階搜尋(音樂類 + house / disco / techno / dance 等關鍵字, 每頁 48 筆)抓作品頁, 從頁面的授權欄位只留 CC0 / CC-BY, 再用 HTTP Range 只下載每個檔前 1.5 MB 粗估拍速與大鼓清楚度, 過門檻的才下載全檔(1000 頁約 15 分鐘); (3) OpenGameArt 上名稱帶兩個作者名的作品多半是第三人把兩首混在一起的混音, 優先用原作頁面, 署名較單純。(BubbleCatcher playtest 三關換曲的選曲調查)
- `辨識` **要「稀稀落落的掌聲」循環, 免費 CC0 只有整群人密集鼓掌的錄音** → 密集掌聲壓低音量仍是一片噪音牆, 聽不出「場子才剛暖」 → 掌聲錄音的漸弱尾段多半是零星幾個人在拍: 用 5 毫秒包絡上升 > 8 dB 抓出單拍(本例 3.8 秒抓到 16 拍), 每拍剪 90 毫秒, 再用「幾個人各自固定節奏、拍一陣停一下」的方式散佈, 位置對循環長度取模, 天生首尾無縫。密度用「每秒幾拍」控制(本例 5 人約每秒 10 拍)。同一份錄音的密集段另作收場掌聲, 兩者質感一致。(DungeonZoo 打磨第 3 輪, 效果待試玩)
- `辨識` **成對事件(「目標出現 / 目標達成」)各要約 1 秒、彼此呼應的音, 現成短樂句湊不出一對** → 音樂短樂句包裡上揚的撥弦 / 鋼鼓多是全音階跑動(像施法, 不像收尾), 薩克斯類起音 40~90 毫秒太慢; 勝利號角多是好幾小節(10 秒以上) → 找「同一段旋律附多種樂器分軌」的素材(例: OpenGameArt 上 Fupi 的 Win Jingle, CC0, 2.1 秒、17 種樂器 WAV, `https://opengameart.org/content/win-jingle`), 挑配合遊戲既有音色的分軌自己混。成對事件取同一段旋律: 「出現」只放前兩個和弦、原速, 停在未解決的和弦; 「達成」放整句, 高品質重新取樣(視窗化 sinc)加速約 2 倍壓到 1 秒左右, 收在主和弦, 前後呼應。(DungeonZoo 打磨第 7 輪 build, 效果待試玩)
- `辨識` **小眾的聲音(爆竹、彩炮這類「劈啪 / 大砰」)用直白關鍵字(firecracker、confetti)在 OpenGameArt 一筆都找不到** → 站內搜尋只比對標題與標籤, 小眾詞多半沒人標 → 改搜近義的大類詞(fireworks、bang; 同理 horse 代替 hooves), 一個 CC0 合集常能湊齊一整組(例: rubberduck 的「25 CC0 bang / firework SFX」, `https://opengameart.org/content/25-cc0-bang-firework-sfx`, 免登入, 有短槍響、大砰與尾段持續劈啪的煙火)。連發類(鞭炮)= 短槍響加速約 2 倍、間隔 0.05~0.09 秒連放幾聲, 音量壓到比主爆炸低約 15 dB; 挑「持續劈啪」那段用每 100 毫秒響度包絡看: 起爆後維持在約 −30 dB 上下一秒的才是持續劈啪, 一路衰減的只是單響。(DungeonZoo 打磨第 8 輪 build, 聽感待試玩)
- `辨識` **要寫實的單一物件錄音(例: 音樂盒), OpenGameArt 只找得到整首曲子** → OpenGameArt 偏遊戲音樂與合成音效, 寫實的物件錄音少 → BigSoundBank(`https://bigsoundbank.com`, Joseph Sardin)整站錄音標 CC0、免登入; 頁面的下載鈕是 POST 表單抓不到連結, 但原檔可直接用 curl 下載: `https://bigsoundbank.com/UPLOAD/bwf-en/<四位數編號>.wav`(BWF = 帶中繼資料的 WAV, 一般 WAV 讀法可讀)、`/UPLOAD/ogg/<編號>.ogg`、`/UPLOAD/mp3/<編號>.mp3`; `/UPLOAD/wav/` 會回 HTML 不能用。編號在頁面網址結尾(例: `-s0416.html`)。(DungeonZoo 打磨第 9 輪 build: 音樂盒錄音拿來做暫停音)
- `辨識` **要「一把金幣噴出來」約 0.6 秒的嘩啦聲, CC0 錢幣錄音多是單枚掉落或很長的倒錢** → BigSoundBank 錢幣類(站內搜尋 `https://bigsoundbank.com/search?q=coins`, 結果頁連結含 `-s<四位數編號>.html` 可直接抓編號)都是單枚掉進杯子、桌上旋轉 12~20 秒或慢慢倒 40 秒以上; Kenney 的 RPG / 賭場包只有手抓錢幣與籌碼單響 → OpenGameArt 上 LordTomorrow 的「Coin Splash」(CC0, `https://opengameart.org/content/coin-splash`, 0.33 秒、21 毫秒到峰值一成)是一把金幣打在地上。長度不夠時同一個檔錯開疊三層、各用不同速度(例: 0 / 0.12 / 0.27 秒、速度 1.0 / 1.18 / 0.9、音量遞減), 聽起來是三把不同的錢, 拉到約 0.6 秒, 不必再找第二個素材。(DungeonZoo 打磨第 12 輪 build, 聽感待試玩)
- `辨識` **要「戰鼓重擊」單響與單獨一支號角, CC0 搜 war drums / horn 只有密集鼓組循環與整首曲子** → 戰鼓素材多是 130 BPM 上下的整段鼓組(每 0.1 秒就一擊, 挑不出單獨重擊), 號角也多夾在多聲部曲子裡 → 鼓改用 BigSoundBank 的低音通鼓單擊(`https://bigsoundbank.com/bass-tom-1-s2338.html`, CC0, 約 175 Hz), 視窗化 sinc 降速 0.62~0.7 倍成 120 Hz 上下的大鼓, 自己排響數與間隔(例: 三響間隔 0.3 秒、最後一響最重); 號角從整首曲子裡以每 50 毫秒的音高相關係數找「≥ 0.99 且持續 1.5 秒以上」的段落, 那就是單獨一支號角在長鳴(例: Eldritch Grim「War Horns」CC0 的 15.0~16.95 秒)。(SoulSmithDefense 打磨第 2 輪 build, 聽感待試玩)
- `品味` **開戰音只用一支合成感的號角, 被嫌難聽** → 單一號角長音沒有打擊起頭 → 改成「戰鼓三響 + 號角一短一長」約 2.6 秒, 兩者響度相近(各約 −14 dB), 開頭 0.6 秒先有打擊再接號角。(SoulSmithDefense 打磨第 2 輪, 規格轉述的回饋「上一輪的聲音難聽, 要重做」; 效果待試玩, 下一輪確認後再決定是否保留)

## 授權與下載

- `辨識` **CC BY 音樂的署名文字** → incompetech 的授權頁會生成固定格式(曲名、Kevin MacLeod (incompetech.com)、Licensed under Creative Commons: By Attribution 4.0、授權網址), 照抄進 credits.md, 並在回報裡提醒製作人遊戲畫面上要放署名。(BubbleCatcher round-7 後的 build)
- `辨識` **素材包頁面標 CC BY, 內文卻寫「混合授權, 見包內 credits.txt」** → 頁面授權欄只能標一種, 轉製者把 CC0 與 CC BY 的來源混成一包 → 解開後讀包內署名檔, 逐檔看原始來源授權, 優先挑 CC0 的檔; 但轉製是頁面作者做的, 保守起見仍照頁面的 CC BY 署名(轉製者 + 原錄音者與原始網址), 授權統計算進 CC BY。頁面同時列 CC BY 與 CC0 兩種的, 選 CC0 並在 credits 寫明「選 CC0」。(DungeonZoo 打磨第 8 輪 build)

## 技術

- `辨識` **即時回饋音聽起來延遲** → 素材開頭有長段低音量前奏(例: 翻書聲在「啪」之前有細碎紙聲), 剪靜音時用峰值 0.3% 當門檻會把前奏當成聲音保留, 實際峰值落在 0.5 秒後; 其次才是 mp3 開頭填充與 HTMLAudioElement 剛建好尚未載入(第一鍵既是 init 又是觸發鍵時最明顯) → 挑素材時量「出到峰值一成的時間」, 按鍵直接回饋的音要在 0.03 秒內, 超過就換素材而不是硬剪; 這類音另以 16-bit PCM base64 內嵌、init 時直接填進 AudioBuffer(不經 decodeAudioData, 同步可用), 以 Web Audio 播放, 沒有 Web Audio 再退回播放池。刻意漸強的音(掃掠、上揚)不受此限, 但要有立即出聲的層墊著。(SlimeTetris round-11, 老闆原話「說明頁左右翻頁時的音效延遲太久」; 量得原素材 0.52 秒才到峰值一成, 換素材 + 內嵌兩項一起做, 哪一項貢獻多少待試玩)(續)開頭只有 0.03~0.15 秒靜音或細碎前奏、本機又無法重新編碼 ogg / mp3 剪頭時 → 不改原檔: 事件表每一層加「起播位置」, Web Audio 用 `source.start(時間, 起播秒數)`, 退回 HTMLAudio 時設 `currentTime`; 起播位置用 5 毫秒包絡量(取開始爬升前一格), credits 的剪輯欄寫「無(播放時跳過開頭 N 秒)」, 原檔與授權紀錄保持一致。前奏長到 0.5 秒那種仍是換素材。(DungeonZoo 打磨第 5 輪 build: 按鍵布料聲 31 毫秒到峰值一成, 跳過 25 毫秒後在範圍內)
- `辨識` **背景音樂要跟拍子時鐘對齊、還要整數小節無縫循環, 但 file:// 不能 fetch、HTMLAudio 循環有縫** → mp3 以 base64 內嵌進 sound.js(三首約 6 MB), 頁面載入時用 OfflineAudioContext 先 decodeAudioData(不需使用者操作、不會被自動播放擋), 用 AudioBufferSource 的 loopStart / loopEnd 循環; 檔頭放 0.05 秒數位靜音, 解碼後找第一個 |樣本| > 0.02 的位置跟編碼前比, 自動校正各瀏覽器解碼器的開頭填充差異; 循環終點後多放 0.5 秒循環起點的聲音, 解碼位置有幾毫秒誤差也不會跳。Python soundfile(libsndfile 1.2)寫出的 mp3 是無縫的(本機解碼前後偏移 0 樣本), 不需要 ffmpeg。(BubbleCatcher round-7 後的 build, 瀏覽器實測待試玩)
- `辨識` **量大鼓清楚度時, 好曲子量出負值、整首被誤判成沒有大鼓** → 拍格相位取自全頻段起音曲線, 常鎖到反拍的腳踏鈸或貝斯, 拍格整體偏了半拍或四分之一拍, 「拍上」量到的其實是反拍 → BPM 定好後, 相位另外用低頻找: 在 16 個十六分音符位置各加減幾毫秒試一遍, 取「整首清楚度中位數最大」的相位, 再做逐小節掃描。以已知合格曲(每拍大鼓的 EDM)當對照跑一次, 確認量法本身沒偏。另外: 曲庫標 Grooving、樂器有 Drums, 都不代表每拍有大鼓, 一律要實際量。(BubbleCatcher playtest 選曲調查: 修正前約一半候選量出負值, 修正後同一批曲子的排名大幅改變)
- `辨識` **老闆選定的曲子拍速太快, 要保留音高放慢, 但本機沒有 ffmpeg** → 不用自己寫相位聲碼器 → Rubber Band 官方提供 Windows 命令列免安裝包(`https://breakfastquay.com/files/releases/rubberband-4.0.0-gpl-executable-windows.zip`, 內含 sndfile.dll, 解到暫存資料夾即可用), 用 `rubberband-r3.exe --centre-focus -t <原BPM/目標BPM> in.wav out.wav` 離線整首處理(Python soundfile 先把 mp3 轉成 wav)。放慢後 BPM 正好等於原 BPM × 比例、漂移不增加(量得 105.00 / 115.00, 漂移 ≤ 0.2 毫秒/分)。大鼓清楚度: 放慢 22% 的四拍電子曲維持 36/36 小節清楚(清楚度中位 −2.7 dB); 放慢 13.5% 的另一首從 38/40 掉到 37/40, 掉的是原本就在門檻邊緣的小節。R2 引擎(`-c 6` 打擊清晰)當對照, 清楚度不比 R3 好。放慢後一定要重量清楚度, 只會讓「本來勉強過」的小節變成不過, 不會無中生有。(BubbleCatcher v26 build, 試玩效果待確認)
- `辨識` **量出來的小節線(第 1 拍)錯位, 截取窗與循環點都會跟著錯** → 用「每 4 拍的頻譜變化量」猜小節線, 遇到通篇差不多的電子曲會四個位置分數相近(0.97 / 0.98 / 0.92 / 1.00), 結果挑錯了 3 拍 → 改量 6 kHz 以上高通的起音: 爆擦鈸幾乎都打在段落的第 1 拍, 取起音最大的 30 拍看落在 4 拍中的哪一格(本例 24/30 落在同一格), 再跟「曲子從第 1 拍開始」互相印證; 小鼓在 2、4 拍的曲子則是高頻最強的兩格之間的那格是第 1 拍。(BubbleCatcher v26 build)
