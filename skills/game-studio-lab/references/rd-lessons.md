# RD 經驗

只有 RD agent 讀寫。每條三行內: `- (症狀) → (原因) → (解法)`。跨遊戲通用, 不寫單一遊戲的參數。同類問題合併, 不重複。

## Canvas / 渲染
- 高 DPI 螢幕畫面模糊 → canvas 實際像素等於邏輯尺寸 → `canvas.width = logical * devicePixelRatio`, 再 `ctx.scale(dpr, dpr)`, CSS 尺寸維持邏輯值
- 文字或線條位置偶爾糊一像素 → 座標落在半像素 → 靜態元素座標 `Math.round`, 或 1px 線條偏移 0.5
- 同一個事件被拆成「指示線/框」與「格位本體」兩處呼叫美術函式, 美術文件註明兩者要用同一段換算後的 t(例如事件 t 的某個子區間縮放), 卻各自重算一次 → 玩家會看到兩者對不齊、讀成兩個獨立事件 → 换算成 t 的公式只寫一次存成變數, 兩個呼叫點共用同一個值, 不要在呼叫端各自複製公式
- 捲動鏡頭剛好停在 0(地圖頂端)時, 特效畫錯位置 → 共用繪製函式用「位移值是否為 0」判斷要不要套鏡頭位移, 0 卻是合法的鏡頭位置 → 另傳明確的布林參數表示模式, 不要用數值是否為 0 推斷模式

## 載入 / 檔案
- 雙擊 index.html 開啟後 console 報 CORS, 腳本沒跑 → `type="module"` 在 `file://` 下被瀏覽器擋 → 一律用傳統 `<script src>`, 用全域物件溝通

## 輸入
- 系統事件(視窗失焦等)要求固定結果(如規格明講「不論當下座標一律視為某結果」), 實作時卻呼叫了與一般操作共用的判定函式 → 共用函式會按當下座標重新判斷落點, 萬一當下位置剛好落在合法目標上就判成另一種結果, 和規格「一律強制某結果」矛盾 → 系統事件觸發的強制結果直接寫一條獨立路徑套用該結果, 不要借用「讀取當下座標」的一般判定函式
- 按方向鍵或空白鍵頁面會捲動 → 瀏覽器預設行為 → keydown 裡對遊戲用到的鍵 `e.preventDefault()`
- 按住鍵一直觸發跳躍 → keydown 會重複觸發 → 用 `e.repeat` 過濾, 或維護 pressed 集合只在狀態轉變時動作
- 長按鍵對應的「按住計時」(長按觸發/DAS 等) 一直被重置、或暫停鍵長按會瘋狂切換 → `e.repeat` 判斷寫在某些 case 分支之後, 其他分支繞過了它 → `if (e.repeat) return;` 放在 keydown handler 最前面、任何分派邏輯之前, 不要分支各自判斷
- 角色進入不可操作的中間狀態(結算/暫停)前就按住某個「持續生效」鍵(如軟降), 解除後不需要重新按下就自動恢復生效 → 規格通常只對其中一種持續輸入(如左右移動的 DAS/ARR)明文允許跨越凍結狀態延續, 其餘的都要視為「按下事件」被丟棄且不補發, 但實作只顧著擋離散動作(旋轉/硬降), 沒擋這種「持續按住的旗標」, 旗標值就這樣原封不動撐過凍結期 → 進入凍結狀態的那一刻主動把該旗標清成 false, 且對應的 keydown 分支也要判斷目前是否處於可操作狀態才允許把旗標設回 true, 不要以為「沒有主動改就是延續」是安全的預設值
- 同一個系統事件(如視窗失焦)規格要求依當下子狀態分岔出不同強制結果(如「按著未拖」比照放開、「拖曳中」才彈回), 實作卻只接了其中一種子狀態分支, 另一種子狀態被那個分支的邏輯直接吃掉或整個忽略 → 寫分支時只想著最常見那種子狀態(拖曳中), 沒有逐一對照規格把每種子狀態都列出來各自處理 → 收到系統事件時先判斷當下實際子狀態(是否已判成拖曳), 每種子狀態各自呼叫對應的既有收尾函式(如「放開」與「彈回」分開呼叫), 不要只處理最顯眼的那一種就當作涵蓋全部
- 規則以「兩幀間路徑」判碰撞 / 碰網, 玩家卻回報「明明碰到了沒觸發」, 紀錄裡是一批「放開點已越過目標、卻被當成普通放開」的拖曳 → 放開事件自帶的座標比最後一筆被處理的移動更遠(瀏覽器每幀只合併送一筆移動, 放開即時送出; 快速甩過去就整段漏判), 放開的判定又直接拿放開座標分類 → 拖曳中收到放開時, 先把「物件最後處理位置 → 放開座標」當一筆移動走完整路徑判定(碰目標則已結束、放開不產生事件), 再做放開分類; 系統強制路徑(視窗外 / 失焦)不補掃
- 拖曳起手式(抓起那一筆移動)把「已貼著目標就忽略碰撞、要離開再碰回」的旗標用當下座標初始化 → 第一筆移動就跳很遠(幀卡頓 / 快速甩出)時旗標被設成 true, 之後整段碰撞被吃掉 → 這類「要先離開再碰回」旗標只由規格明寫的情境(換位當下不符)設成 true, 起手式一律歸零, 下一筆移動自然會判 同類: 每段移動結尾又用「位置式」謂詞(<= 容差)覆寫同一個旗標, 而偵測走「路徑二分搜尋」(永遠評不到端點 t = 1) → 指標整數座標剛好讓氣泡圓與目標相切時, 路徑式判成沒碰到、位置式判成碰到, 旗標被自己設成 true, 之後整段(氣泡越拉越深)都被擋 → 持續狀態旗標只准由規格明寫的情境設成 true、其他地方只負責解除; 路徑式掃描要單獨比端點; 另加一道「位置貼著目標且屬性相符就補判」的保險(正常計數應為 0)
- 同一顆鍵同時是「開始 / 翻頁 / 關說明」與遊戲內動作(如空白鍵開始 + 空白鍵攻擊), 開始那一下同幀就被當成動作 → 按鍵事件設的動作旗標在同一幀的轉場處理後沒清, 後面的遊戲更新又讀到 → 事件處理結尾若階段變了(或剛關說明)就把動作旗標清掉, 只有階段不變時才留給遊戲更新讀

## 計時 / 遊戲循環
- 切到別的分頁再回來, 物件瞬移或穿牆 → requestAnimationFrame 暫停後 dt 累積過大 → `dt = Math.min(dt, 1/30)` 之類上限; 自動化測試用固定步階假造 rAF 時, 步階若超過這個上限, 每幀都會被裁掉一截, 模擬的遊戲內時間會比設定的秒數慢好幾倍且不自覺 → 假 rAF 的步階要小於等於這個上限(如 16ms)
- 不同螢幕更新率速度不同 → 用幀數而非時間推進 → 所有移動乘 dt
- 數值條被玩家動作推到上限的那幀沒觸發「滿了就…」, 要再多推一點才觸發 → 玩家動作在更新前段把值加到上限, 上限判定卻放在更新尾段, 中間的自然衰減先把值壓回上限以下 → 上限判定在「玩家動作處理完」立刻跑一次, 更新尾段(技能 / 事件改值後)再跑一次; 測試用真的連按動作推到上限, 不要直接改值(會繞過這個時序)
- 規格寫「數值升到上限的瞬間才觸發」(如加一個標記), 標記遞減到 0 後數值仍停在上限, 標記立刻又被補回、永遠減不到 0 → 觸發寫成每幀用狀態重判(值 ≥ 上限且標記 = 0), 沒區分「上升的那一刻」與「停在上限」 → 「升到的瞬間」只在造成上升的事件處理裡判一次, 每幀更新不要用狀態謂詞重判同一個觸發; 情境測試走一遍「達上限 → 標記遞減到 0」確認真的歸 0; 同類: 規格寫「撞到目標就換下一段」的追逐 / 衝撞, 物件擠成一團時一幀換一段(一場上百段) → 「撞到」用距離判斷, 撞擊本身卻有冷卻, 冷卻中仍貼著就每幀滿足條件重找 → 「換段」只掛在真的發生撞擊(過了冷卻)那一刻, 不掛在單純距離條件; 測試量一場的段數與撞擊數確認同量級
- 角色/方塊被鎖進不可操作的中間狀態(結算、演出、對話)一段時間後解除, 持續按住的移動鍵放開時會暴衝或瞬移一大段 → 該狀態期間 DAS/ARR 等「持續按住」計時器仍在扣 dt, 累積成一段很負的值, 解除瞬間迴圈追趕 → 該計時器只在真正可移動的狀態下才扣減, 其餘時間整個凍結不動, 恢復時自然從原進度接續, 不追趕不歸零
- 多階段流程裡某個計時要凍結(如等待玩家輸入), 卻連帶凍結了流程結束後的收尾動畫/UI 停留 → 用同一個「是否處於此大階段」的旗標同時控制輸入路由與計時凍結, 但兩者涵蓋範圍其實不同 → 拆成兩個判斷式: 一個對應規格精確定義的凍結窗口, 一個對應較大範圍的輸入攔截/UI 顯示
- 系統有外部節拍/格線權威(如音樂拍子、固定格位)時, 某段排程的時間算出來能跑、數字卻對不上規格(間隔錯誤, 或下一次事件沒有精準落在格線上) → 參考舊版本代碼移植公式時, 舊常數同時服務「間隔」與「週期換算」兩種不同用途, 只在某個特例數值剛好相等才沒露餡; 且排程值只寫入連續運算出的秒數, 沒有在寫回前對齊到格線 → 每個常數只能對應規格裡唯一那條公式, 不同用途各自命名定義, 不要共用; 任何規格要求「必須落在格線上」的時刻, 寫回排程前要先換算成格線上的整數單位(如先定目標格數, 用格數反推時間), 不能直接採用原始連續值, 並寫情境測試驗證連續多次排程後仍逐一落在格線上
- 時間軸中途重置(換關/換曲後關內時間歸零或變負)後, 被帶過重置的存活物件(如換關當下仍在拖曳的那顆)節點被判到舊軸的拍、時間差離譜 → 物件身上快取的「上次事件時間」還是舊軸的值, 又被「不得早於上次事件」的夾限拉回舊值 → 重置函式要掃過所有帶過去的物件, 把快取時間改成新軸當下值或清空; 測試要專門造「帶過去」情境, 檢查節點的最近拍序號落在新軸範圍
- 剛好在段切換拍(如第 64 拍)那一幀抽網條件, 條件池是空的, `pickRandom` 回 undefined, 之後讀 `cond.color` 例外, 又被主迴圈外的 try/catch 吞掉, 整局看起來卡住 → 「現在是前段還是後段」有兩個來源: 拍點觸發設的旗標(容許 1e-9 誤差)與各處用 `lt/bs >= 64` 重算(浮點 63.9999 判成前段), 邊界那幀兩者不一致 → 段/階段這類狀態只留一面旗標當唯一權威, 抽條件、地板狀態、扣血、事件標籤一律讀旗標, 不各自用浮點時間重算; catch 住例外時一定要 console.error
- 依時間依序觸發的事件(結算星星逐顆彈出的音效)同一顆播了兩次 → 用「上一幀時間 < 門檻 + 容差 且 現在 ≥ 門檻」判斷剛跨過, 浮點累加讓上一幀落在門檻上方一點點, 容差又把它算進去 → 依序觸發改用計數器: 「已觸發數 < 總數 且 時間 ≥ 間隔 × 已觸發數」就觸發並加一(用 while 迴圈補齊), 不用前後幀比較加容差

## 其他
- 物件「消失/移除」後從陣列裡拿掉, 但某條分支(如放開滑鼠時要記一筆「這顆其實已經在拖曳中過期」的收尾事件)需要在那之後仍讀到它 → 該分支用 id 回頭到陣列裡 `findById` 找它, 陣列已不含這顆, 永遠找不到、分支變死碼且測不出來(靠讀碼也看不出, 因為程式碼本身邏輯完整) → 建立當下的呼叫方(如按下滑鼠那一刻)直接保留物件的參照存起來, 不要事後才用 id 回陣列查; 這類「事後收尾」分支要额外寫情境測試才會被踩到, 光靠一般 fuzz 不會觸發(機率太低或需要精準時序)
- 埋點的「排定拍序號 / 下一次特色發生拍」在成立當下寫死, 後來某分支把該次取消或順延(例: 預告期間先被玩家操作消耗掉, 該拍不再執行), 紀錄仍指向已過去的拍, 等待長度對不上 → 只在建立時算一次、之後沒人回頭改 → 凡有「取消 / 順延」分支的排程, 分支內同步改已記下的排程欄位, 並寫情境測試強迫走到該分支驗證
- 常駐的推導狀態(如依連通塊重算的懸空/分類標示)在某個會改動盤面的事件後沒更新, 一直殘留到下一次別的事件才刷新 → 這種標示是靠多個「會改變格位」的路徑各自在事後呼叫同一個重算函式維持一致, 新增或後補的那條路徑(如削頂、局部移除格位)漏呼叫了 → 新增任何會改動格位的路徑時, 對照既有其它路徑(消除、重力事件、全盤清除等)逐一確認是否都呼叫了同一個重算函式, 不要假設只有主線路徑需要
- 動態陣列前端插入(如向左延展一欄)後, 舊格子索引全部跑位 → 事件當下算好存起來的座標沒有跟著平移 → 插入當下立即修正所有已存座標, 或乾脆不快取, 繪製時一律用當下最新狀態重新換算
- 物件在動畫/事件期間顯示成美術預設色(或其他預設值), 落定/結束後才變回正確值; 或埋點事後比對不上(如某個實例被「別的」事件搬動過一次後, 之後不管哪個路徑把它結算掉, 都對不回原本該記的那筆紀錄) → 內部工具函式把資料往下一層傳遞、或搬移/重新落點時只挑了當下這一步用得到的幾個欄位(如只留 col/row/color), 把「別的」下游消費者要用的欄位(如繪製用的 color、或埋點用來對回原始來源的識別碼)漏掉, 之後不管拿到 undefined 落到美術預設分支、還是埋點永遠比對不到只能歸類成預設的兜底分類 → 任何「搬移/重新包裝資料」的工具函式, 回傳或寫回的物件要逐一核對*所有*下游消費者(不只眼前這條路徑要用的)需要的欄位是否都有帶上, 不要只挑「這條路徑的判定邏輯用得到」的欄位; 一個實例有多條可能路徑會把它「消耗掉」時(如同時有主路徑與少見的追加/收尾路徑), 每條路徑都要各自檢查有沒有做該做的回填, 不能假設只有主路徑會發生
- 遊戲一開場先進入「開場說明/選單」等靜態畫面, 但 render() 每幀無條件呼叫的狀態轉換函式(如任務、目前方塊)內部直接讀取尚未初始化的欄位 → 這些欄位要等玩家關閉靜態畫面才會賦值, 開場當下仍是 null → 一開賦就丟例外 → 每個會在遊戲正式開始前就被 render 呼叫到的狀態轉換函式, 開頭都要對關鍵欄位做 null 檢查並回傳合理預設值
- 埋點/校正欄位規格明寫「取兩個特定時間點的差」(如「鎖定後消除前」減「鎖定前」), 實作卻借用了另一個已經算好、但時間點不同的變數(如借用定版後的值) → 數字長期偏離或恆為 0/null, 只有對照規格逐欄重算才看得出來 → 每個「差值/累計」類埋點欄位動筆前先把規格寫的兩個取值時點抄下來, 沒有現成變數就在該時點另外快照一次, 不要借用鄰近步驟已存的近似值; 「累計時長」類欄位也要檢查每個對應事件發生處有沒有真的 `+=`, 不能只在初始化時歸零。同類陷阱: 局末彙整篩選/比對時直接寫 `record.someField`, 但 `someField` 其實從未被寫進這個事件(資料實際存在另一個事件類型或另一個變數上)→ JS 存取不存在的屬性只回傳 `undefined`、不拋例外, 跑分/跑迴圈仍會得出一個「看起來正常」的數字或永遠為假的條件, `node --check` 與互動 fuzz 都測不出來, 只有逐欄核對「這個欄位在哪個 emit() 呼叫裡被賦值」才抓得到 → 局末彙整每引用一個事件欄位, 回頭找到該欄位真正被 `emit()` 賦值的那一行確認欄位名與事件類型一致, 不要憑欄位名字「聽起來合理」就假設它存在; 跨階段加總欄位(如一顆氣泡的總應得回血, 含前面沾上階段已發生的回血)只加到最後一個階段就收工 → 寫完用 node 跑一局, 對帳「事件流逐筆加總 == 欄位值」「血量起點 + 回血 − 扣血 == 終點」「分數組成加總 == 總分」, 不平就是漏加
- 同一個處理批次內(如一次 tick 掃過多顆物件、一次事件處理)可能連續觸發多次「扣分/扣血」, 且批次結束時要做一次性收尾(存檔、下載、切結束畫面)→ 在批次中途、第一次達成結束條件當下就地立刻收尾, 會搶在同批次接下來還要 emit 的其他事件(如緊接著要記錄的操作結果)前面把資料存走, 造成那些事件遺失且不易發現(邏輯本身沒錯, 只是時機早了)→ 把「是否已達成結束條件」的判斷獨立成一個函式, 只在每個處理批次的最尾端呼叫一次, 讓同批次其餘事件全部 emit 完再做收尾; 批次內個別發生點只管記錄「這次結果」, 不要自己決定收尾時機
- 用 `filter` 從一個陣列篩出子集合, 事後卻拿這個子集合的索引去對應回另一個各自獨立 `filter` 出來的陣列同索引位置 → 兩次 `filter` 各自跳過的元素不一樣, 篩選後的陣列已經不再和原陣列或彼此的索引對齊, 篩掉的位置不會留空位佔位 → 篩選當下就把後續要靠它比對的來源識別資訊(時間戳、id)一起存進篩選後的每個元素裡, 不要事後憑索引回頭配對
- 為了提前預測多步驟結算管線「後段才會發生」的結果(如某個門檻要在動畫播完前就先算出來), 在盤面複本上重跑後段的判定函式 → 複本只複製了「當下即時盤面」, 沒有先套用同一次結算中「排在它前面那些步驟」已經確定、但真正執行時要等前面步驟跑完才會寫回盤面的效果(如前段會清除的格位) → 呼叫後段判定前, 複本要先重放前面步驟對盤面的影響(把前段會清除/改動的格位也在複本上套用), 不能假設「現在的即時盤面」就是後段判定當下會看到的盤面; 這類提前預測的正確性建議另外寫個對照組測試(用一個「不會觸發」的相同結構驗證不誤判)
- 物件一生會經歷多個子事件(如反覆被拖曳、反覆被彈回), 其中有一份「要等物件真正終結(捕捉/過期/殘留)才能回填結果」的待結算清單, 結果在某個中繼子事件(如條件不符彈回、開始新一輪拖曳)就被提前結算或整份重置歸零 → 把「這次子事件結束」誤當成「這個物件結束」, 呼叫了終結專用的回填函式, 或在子事件起手式清空了跨子事件才需要累積的清單 → 該清單只在物件建立時初始化一次, 只有真正的終結事件能讀取並清算它, 其餘中繼事件不得呼叫終結回填函式、也不得清空這份清單
- 埋點「距上次 X 事件的間隔/路徑長」量測起點, 被規格上不算 X 的另一種釋放結果一併重設(如滑鼠放開的共用 handler 裡, 分辨『完成拖曳的放下』與『按住未拖直接放開』之前, 先寫了對兩者都生效的重設副作用) → 共用前導碼裡的副作用沒有跟著後面的分支判斷走, 邏輯讀起來完整、`node --check` 與一般 fuzz 也測不出來, 只有逐欄核對「規格定義的 X 到底是哪個分支」才抓得到 → 重設動作搬到分支判斷之後, 只在真正符合規格定義的那個分支內執行, 不要放在分支之前的共用前導碼
- 規格把「換關清掉」與一般「離場」分開記(批的最後一顆離場時刻、離場計數)時, 批的離場時刻被換關清掉污染 → 換關清掉也走了一般離場函式, 函式內順手寫了離場時刻 → 特殊終結方式(換關清掉、局結束殘留)不呼叫一般離場函式, 另用各自的計數 / 備註欄位記
- 手寫 vm 測試腳本取得的 debug 狀態拿到的是「回傳當下的快照」(基本型別欄位如 screen 不會跟著變) → 在測試迴圈外存了一次就重複用, 狀態判斷永遠是舊值、整批斷言誤報失敗 → 每次斷言前重新呼叫 debug 函式取值, 不要快取回傳物件; 同類: 事前存起來的「物件」其實是遊戲內部的即時參照, 之後拿它跟「現在」比永遠相等, 斷言恆真 → 要比較前後就先把數值抄成基本型別(如 `var t0 = g.totals.touches`)
; 同類: 測試腳本每幀把血量等狀態改回安全值來維持存活, 遊戲內的狀態切換(如危險進出、音效)被測試自己反覆觸發, 總數斷言誤報 → 計數類斷言只計「武裝(開始測的那一刻)之後」的事件, 用 harness 的聲音 / 事件回呼累計; 同類: 情境腳本在一長串動作前讀了「當下亮著的目標 / 條件」, 動作期間(跨換關、自動換位)那個目標已被遊戲換掉, 之後斷言與走位仍用舊值 → 誤報失敗, 動作跨過會改狀態的事件後要重新讀當下狀態再決定下一步; 同類: 等「下一次某事件」卻拿累計 / 最近值(如 lastJumpBeat)> 常數當等待條件, 舊事件的值讓條件在事件發生前就成立, 斷言在還沒走到的時刻誤報 → 等待前先抄下目前值, 條件寫成「值改變」; 同類: 情境測試把怪瞬移到玩家腳下(或要玩家繞怪一圈), 斷言卻失敗(動作形成不了, 或剛成立就斷) → (1)遊戲每幀把怪夾回牠自己的活動範圍, 測試的瞬移被拉回去; (2)場上其他怪照常施放, 打到玩家就把正在累積的動作進度打斷 → 反過來移動玩家去就怪, 並每幀把其他怪的施放冷卻設成很大再跑; 等待迴圈的上限用「遊戲秒數 + 餘量」, 不要剛好等於時長(按時長換算的迴圈次數實際走到的遊戲時間會略少, 如固定步階 16ms 跑 45 秒只有 44.6 遊戲秒); 同類: 情境測試要「A 射出投射物打中隨機亂走的 B」, 單一種子的斷言偶爾失敗 → B 在投射物飛行期間隨機走開、投射物落空, 不是遊戲 bug → 這類命中測試改跑 20~30 個種子, 斷言「成功次數 ≥ 門檻、且每次成功都符合規則(如段數 +1)」, 不要單種子斷言必中; 同類: 情境測試把角色瞬移到觸發點(樓梯、寶箱)站了幾十幀卻沒觸發 → 遊戲內「進場滿 N 秒自動跳出、會暫停整個遊戲」的引導卡把遊戲停住, 測試迴圈沒有按鍵關掉它 → 測試開頭先把會自動暫停的引導階段標成完成, 或迴圈每幀先檢查引導是否開著再決定下一步
- 規格給初速、重力與「跳高固定 X 格」, 四捨五入後互相對不上(如 15.56 與 34.6 只跳 3.4988 格), 驗算「餘量 ≥ 0.5」恰差 0.001 卡門檻 → 常數是為了湊驗收值寫的, 但各自四捨五入 → 以驗收值反推精確常數(v0 = sqrt(2·g·h)), 並在回報註明; 同類: 規格手算捷徑邊際用平台 / 幽靈「中心」、漏算頭頂寬 ±0.5 與「站在移動平台上位移疊加(平台速度 + 自身速度)」, 逐幀掃描後實測比估計少 0.4~0.5 格 → 掃描前先列最有利端點與疊加速度, 手算值只當參考, 不達標時照規格調整範圍移動地形再重掃; 同類: 教學要求「打到殘血才能收服」, 怪血量 6、單次傷害 2、門檻 30%(= 1.8), 血量序列 6→4→2→0 永遠停不在門檻內, 教學走不完 → 讀完數值表後, 先對「教學 / 必經路徑」做一次整數算術(每次打擊後的序列有沒有落在門檻內), 對不上就選最小改動(只改該處門檻)並在回報註明規格矛盾
- 埋點「捷徑路線旗標」只用「所借幽靈的起跳面 + 角色起跳面」判定, 預期解自己也符合 → 預期解被標成捷徑 → 判定要加能區分預期解的特徵(例: 幽靈那段騰空是單純一跳, 或是拉動 + 空中跳), 並重播預期解驗證旗標為空
- 自動移動的目標(脫隊、逃跑、衝向某處)停在玩家可活動範圍的外緣, 玩家卻要靠繞圈 / 碰觸 / 接近才能處理牠, 規則上無解 → 目標停靠點依目標自己的規則算, 玩家角色卻被碰撞半徑 + 邊界限制在更內縮的範圍, 例如圍圈的頂點全在界內、永遠包不到界外的點 → 凡是「玩家要用某動作處理自動移動的目標」, 目標可停靠範圍要夾在玩家實際可達範圍再內縮一個動作尺寸(如繞圈半徑)之內; 用 vm 把目標瞬移到各邊再讓機器人執行該動作驗證, 注意規則本身的動作上限(如軌跡長度)可能小於所需, 測試時補足; 同類: 玩家回報「很難做到」但判定讀碼無誤, 是規則的長度 / 距離門檻(如圍圈軌跡上限 = 隊伍總長)初始值小於操作所需的最小值(一圈周長 = 2π·速度 / 轉速) → 規則有長度門檻時, 先拿玩家操作的極限算最小可行值, 再檢查初始數值, 用 vm 對照舊值不成立、新值成立; 同類(測試機器人): 繞圈機器人把「自己當前角度 + 固定角度」當下一個目標點, 目標被牆夾住後與自己重合、落在方向鍵死區就原地不動, 動作逾時 → 目標改用固定的羅盤路點序列(如 8 點, 夾在可走範圍內), 離路點小於一個門檻才換下一點; 貼牆的目標只能用很小的半徑繞, 規格要求繞圈處理時要回報這個鬆緊; 同類(測試機器人): 把角色瞬間擺到繞圈軌跡上, 繞了約 2 圈繞圈進度仍累積不到 1 → 擺上軌跡那一幀的跳角(最多 ±180°)也被累加進去, 方向又和之後繞的方向相反, 淨進度不到一圈 → 繞圈總角度至少排 3 圈(≥ 1080°), 迴圈每幀先確認被繞的對象(套索等)還在再讀它的座標; 同類: 等「投射物飛完才結算」的數值時用固定秒數斷言, 投射物隨機亂走、偶爾還沒結算 → 等到投射物最長存活時間 + 餘量再讀
- 兩個自動移動的物件疊在同一點後永遠分不開(彼此持續觸發互動) → 追逐、遠離、繞行、急衝的方向都用「對方座標 − 自己座標」正規化, 距離 0 時成零向量, 移動函式遇零向量直接 return 或速度為 0, 兩邊互相卡死 → 所有「朝 / 離 / 繞某物」的方向計算在移動工具函式內統一處理: 距離 < 1 時改用隨機單位向量; 「落點 = 對方當下位置」類規則(彈飛、瞬移、急衝)會製造距離 0, 要用 vm 把兩者疊在同點、逐種組合跑一段時間, 量最長重疊時間
- 嵌入式教學一次只顯示一個階段, 玩家離開該階段所屬的場景(進結算、回選單)後它仍占著「目前階段」, 之後別的場景的階段永遠出不來 → 「目前階段」與場景綁死, 離開場景時沒有收尾 → 每幀檢查目前階段的場景條件, 離開就收起(出現旗標保留, 回到該場景再出現); 只屬於某個流程的階段(如只在教學日)在流程出口強制標成完成; 時間型階段(顯示 N 秒)只在所屬場景內累計; 同類: 階段的完成條件剛好是「按鍵進下一個畫面」(按鍵出發 / 進入下一頁), 完成特效沒有畫面可播, 玩家看不到打勾 → 完成瞬間就被場景切換吃掉 → 這類階段的轉場延後到特效播完(畫面保持、不接輸入), 留在同一畫面的階段不用; 測試斷言「特效期間仍是原場景、播完才換」; 同類: 階段的完成條件是瞬間狀態(手上拿著東西), 玩家在前一階段還沒完成時就先做完, 前一階段完成後這階段永遠等不到條件, 後續階段與倒數全卡死 → 狀態型條件只在該階段是「目前階段」時才檢查, 提早做掉就錯過 → 狀態型完成條件同時接受「更後面的結果已成立」(例: 東西已裝進目標也算拿過); 測試造「先做後面的動作、再完成前一階段」情境驗證不卡; 同類: 後面階段的完成動作(如合成)發生在更高優先的彈窗階段期間, 完成事件只通知目前階段, 被彈窗階段吞掉, 事後完成條件已不成立, 永遠完成不了 → 這類「可能在別的階段期間做掉」的階段, 完成事件先記進延後旗標, 輪到它時下一幀補記完成(不播泡泡特效); 測試造「彈窗階段期間做掉後面階段動作」情境驗證; 完成動作本身就讓狀態型條件失效時(在替換彈窗裡把手上的東西裝上去, 手上換成別的)也屬此類, 只靠狀態型條件或只在部分動作點記延後旗標都會漏 → 每個完成動作發生點(裝上 / 蓋下 / 合成)一律對所有可能被別的階段蓋掉的階段呼叫同一個完成事件函式
- 單位無敵(或其他「不可被當目標」)期間, 自己該做的攻擊或行動也被擋住(無敵中的玩家不開火) → 把「可被當成目標」的判定(無敵中 = 否)順手拿來當「自己能不能行動」的守衛 → 「可被攻擊」與「可行動」分成兩個判定; 行動守衛只看倒下 / 死亡旗標, 不看無敵; 寫完對「無敵中」「倒下中」各跑一次情境確認

## 環境 / 工具
- 用 `python3 - <<EOF` 批次改檔, 結果無輸出、檔案沒變(exit 49); 或超長 heredoc 報 `unexpected EOF` → Windows 的 `python3` 是商店捷徑不是直譯器, 超長 heredoc 內容也容易被 shell 吃掉 → 批次改檔寫成 node 腳本(精確字串取代, 找不到或不唯一就中止), 長內容用 Write 工具落檔再執行, 套用後一定 `node --check` 並 grep 確認真的改到; 同類: `node -e "多行 JS"` 內含引號、反引號、換行時被 shell 吃掉(unexpected token) → 一律寫成 .js 檔再執行, 改檔內容含 CRLF 的文件(如 rd-lessons.md)要用 `\r\n` 比對
; 同類: 同一檔先用外部 node 腳本寫入、再用 Edit 工具改, Edit 報「File has been modified since read」 → 工具以讀檔時的版本判斷, 外部寫入讓它失效 → 外部寫完後下一次 Edit 前先 Read 該檔一小段, 或同一批改動只用一種方式; 同類: 含反斜線的程式碼(正則 `\/`、`\d`)放進 heredoc 的 node 取代腳本, 寫進檔案後反斜線被吞(出現 `/Edg(?:e)?/([d.]+)/` 這類語法錯誤) → 工具層對反斜線多跳脫了一層 → 含反斜線的片段改用 Edit 工具直接改, 正則的數字類別寫 `[0-9]`; 同類: 用 `node -e "..."` 把含 `\n` 的字串插進 patch 腳本, shell 把 `\n` 展開成真換行, 單引號字串斷行 → 語法錯 → 直接用 Edit 工具改腳本檔; 專案與 scratchpad 在不同磁碟時, node 腳本路徑一律寫絕對路徑, 不用 `../../` 相對路徑; 同類(無頭 `claude -p` 執行時): Bash 報「Parser skipped input between top-level statements」或「requires approval」、命令沒執行 → 含 heredoc、`$TEMP` 變數、`cd … && node -e "多行"`、`sed -i '…'`(單引號內含大括號與引號)等複合寫法被工具層攔下 → 測試與改檔腳本一律用 Write 工具落檔到暫存資料夾的絕對路徑, Bash 只下單純的 `node 絕對路徑`(不串 cd、不用變數)
- 想用瀏覽器(含無頭 Chrome / Edge + 遠端除錯)跑真實輸入來重現 bug → 殘留的無頭行程會在背景持續播遊戲音樂, 製作人明令禁止 → 自測一律只用 Node vm + 假 canvas + 假 Sound, 不啟動任何瀏覽器; scratchpad 是跨次共用的, 新寫的測試檔用專屬前綴命名, 不要覆寫既有的 harness / soak / bot 檔(覆寫了就用同目錄的備份版或 git 版本重建, 並重跑舊 soak 確認); 同類: 用 Write 建暫存腳本回「File has not been read yet」 → 暫存資料夾已有跨輪留下的同名舊檔, Write 拒絕覆寫沒讀過的既有檔 → 暫存腳本檔名帶本輪專屬前綴(如 `<遊戲縮寫><輪次>_patch1.js`)用 Write 建新檔, 不改用 heredoc 繞過
- 在 git-bash 用 heredoc 把暫存檔寫到 `/tmp/...` 再叫 node 讀, 報 ENOENT(被解成 `E 槽的 tmp 目錄`) → git-bash 與 node 看到的 /tmp 不是同一處 → 暫存檔一律寫 scratchpad 的絕對路徑; 同類: 前景跑超過 120 秒的掃描被丟背景, 想收掉時 `taskkill /IM node.exe` 會連別人的 node 一起殺 → 長時間掃描一開始就 run_in_background 並輸出到檔, 等待用 until 迴圈(單次不超過 100 秒), 只殺自己啟動的 PID

## 自測
- 複雜狀態機(多步結算、連鎖事件)單靠讀碼很難確認是否可達、會不會卡死或漏轉場 → 沒有瀏覽器可跑真實互動 → 用 Node 的 `vm.createContext` 搭配最小 stub(window/document/canvas.getContext/Art 全部 no-op)把整支 game.js 真的跑起來, 手動合成 keydown/keyup 事件與固定步長呼叫 tick, 跑幾千幀隨機操作 + 特定情境(暫停/說明/放棄/重開)觀察是否拋例外, 比純讀碼可靠; ctx 的 `measureText`/`createLinearGradient`/`createRadialGradient` 等方法呼叫端會取用回傳值(如 `.width`、`.addColorStop`), 全部一視同仁 no-op 會在美術程式碼內部噴「讀取 undefined 屬性」, 這幾個要單獨回傳最小可用物件(如 `{width:10}`、`{addColorStop(){}}`); 腳本內部裸寫 `window.Foo=Foo` 這種寫法, 在 vm 裡若另外造一個獨立物件當 `sandbox.window`, 裸的全域識別字 `Foo` 抓不到值(ReferenceError)→ 讓 `sandbox.window = sandbox` 本身(比照瀏覽器 `window === global`), art.js/game.js 的 `window.X` 賦值才會同時變成可裸讀的全域 `X`; 同類: `assert.deepStrictEqual` 比對 vm 沙盒內產生的陣列 / 物件報「same structure but not reference-equal」→ 沙盒與主程式的 Array / Object 原型不同 → 比對前先 `JSON.stringify` 或逐欄比
- 想在測試中觀察遊戲內部真實狀態(目前畫面、目前這局物件)才能正確分派下一步合成事件 → 這些狀態多半是模組 IIFE 內的閉包變數, 外部測試腳本讀不到 → 暫時加一個只回傳(不可寫)目前狀態的 `window.__debugState()` 之類唯讀觀察窗, 測試跑完、確認過行為後再拿掉, 不要留進交付版本; 做法改進: 組裝腳本一次產出兩份, 交付版不含觀察窗、測試版才有, 就不會漏拆; 另外 vm 沙盒要傳入自製可播種的 `Math`(`Object.create(Math)` 蓋掉 `random`), 否則遊戲內的隨機(陣型 / 網條件)每次不同, 測到的例外無法重現; 同類: 隨機按鍵 fuzz 只走得到前幾個畫面(如教學關要達成條件才過), 想測後段畫面又不想加觀察窗 → 傳統 script 頂層(沒包 IIFE)的 `let/const` 與 function, 在同一個 vm context 後續的 `vm.runInContext('...')` 裡可直接讀寫、呼叫 → 載入 game.js 後用 `runInContext` 直接呼叫遊戲自己的進場函式、改狀態造情境, 再用假 rAF 跑幀並記錄 Art 呼叫參數對帳, 不必改交付檔; 狀態包在 IIFE 閉包內時才需要觀察窗
; 另外沿用舊 harness 時, 切入 game.js 結尾的固定字串(含換行與空行)在新版檔尾多一個空行就找不到(hook not found) → 開工先對新版跑一次 smoke, 定位點用 lastIndexOf 找單行片段(如 `requestAnimationFrame(frame);`), 不比對跨行字串; 另外舊測試腳本指向「目前的 game 資料夾」跑新版, 一批失敗分不清是新 bug 還是舊斷言過期(寫死舊版補償、預告拍數、localStorage 鍵, 甚至舊版本身就失敗) → 先把同一支測試改指向上一版產物跑一次當基線, 舊版也失敗的不算新 bug; 因規格改變而失敗的斷言, 複製成新前綴的測試再改數值, 不改舊檔
- 需要驗證的規則分支很少被隨機測試觸發(如需求顆數高、進階獎勵深)→ 正常規則下要很多步驟才會走到 → 在記憶體中用字串取代法暫改門檻常數(不動硬碟上的檔案)重新丟進 vm 執行一次, 專門逼出該分支後照常跑完整流程
- 用字串取代硬改門檻常數做深度 fuzz 時, 存活率太低導致遊戲一直很快結束、深層分支(如多輪獎勵、封頂狀態)測不到 → 純隨機左右移動很容易疊高即死 → 開一個 debug hook 讓測試腳本讀到當下真實物件(如目前方塊欄位、盤面寬度), 用讀到的資料計算「要往哪欄移動幾格」再送鍵, 但只能讀不能改該物件欄位(它是遊戲內部真實參照, 直接改欄位等於繞過碰撞判定竄改盤面); 另外固定的按鍵測試序列(如連按兩次 Esc 想著「應該會回到原狀態」)遇到其他分支(如 H 開説明的中途狀態)會不成立, 送下一個鍵前先讀當下真實狀態再決定送什麼鍵, 不要假設固定序列必定把狀態帶回原點; 若只是想逼出「進度軌某個很後面的分支」(如任務序號、已執行獎勵次數), 用 debug hook 直接把這類與碰撞無關的計數欄位改到目標值再讓下一次結算自然發生, 比硬改門檻常數整套重跑更快更準; 同類: 測試腳本用「按方向鍵直到游標到目標」的迴圈, 整支卡死、前景逾時 → 前面的操作留下選擇面板 / 對話框開著, 方向鍵被面板吃掉、游標永遠不動 → 等待類迴圈一律加次數上限, 迴圈前先關掉面板; 長腳本拆成多支小情境腳本(各自用 debug 狀態直接造情境), 比一支從頭按鍵走到尾好維護
- 等一段結算(含獎勵事件)跑完卻用猜的固定幀數 → 結算總時長依是否有清除/重力事件/哪種獎勵而定, 固定幀數常常等不夠, 誤判「這個分支沒被走到」→ 改成迴圈逐幀跑、每幀讀真實 mode, 直到真的回到 playing/over 為止才停, 不要用猜的幀數上限包一段固定迴圈
- 玩家回報「有時候沒觸發」, 老闆也沒給步驟, 只有試玩紀錄 → 純讀碼找不到(幾何函式窮舉 / 隨機路徑都零漏判) → 先把紀錄裡的疑似實例歸成條件(放開座標、已越過線、符合條件、無碰網事件), 把同一條件寫成偵測器掛進 vm 隨機操作, 再用「把放開座標拉得比最後移動更遠」這類環境差異造出同樣的紀錄特徵, 原版偵測數大、修後為零才算重現; 另外量一次「畫面看起來碰到的位置」與「判定位置」的差(美術畫的線寬、拖曳放大倍率會讓視覺接觸早於判定十幾像素), 屬規格 / 美術問題要回報, 不要自己放寬判定 同類: 偵測器掛進隨機 fuzz 仍為 0, 是因為 fuzz 用浮點座標、真實滑鼠是整數座標, 軸對齊目標(法線 = 座標軸, 如槽 1 / 5)才會剛好落在相切邊界, 紀錄裡「只出現在軸對齊那幾個槽位」就是線索 → 測試要把指標座標取整並對軸對齊目標做整格掃描(原版必有失敗、修後為零); 上一輪把症狀歸給單一原因(放開補掃)卻沒真的消掉時, 用同一偵測器回頭檢查舊結論, 不要沿用; 同類: 玩家回報「條件成立卻沒觸發」, 讀碼與逐幀量測(條件成立期間距上次觸發的最大間隔)都顯示有觸發 → 症狀是別的 bug 的連帶現象(如兩隻疊在一起, 畫面上看不出表演) → 先寫量測腳本判定規格要求的時序是否真的違反, 沒違反就修根因, 並在回報註明無法重現該症狀, 不要憑猜測改計時邏輯
- 逐幀驗證(腳本輸入 + 位置 / 時刻觸發)的「執行窗」量出來異常長, 或掃描結果與參數完全無關 → (1)把某步覆寫成絕對幀後, 步驟是依序觸發, 該步被前一步卡住、前一步完成當幀就觸發, 所有更早的幀都被算成功; (2)預設值與覆寫值的合併函式參數順序寫反, 掃描參數根本沒傳進去 → 成功條件加「該步實際觸發幀 == 要求幀」; 掃描結果與參數無關時先印出實際生效的值; 另外前代動作的窗若後代腳本固定在某時刻會被壓得很窄, 要讓後代取最佳應對再量
- 想在沒有瀏覽器時驗證整個遊戲流程(標題 → 說明 → 關卡 → 自評 → 下載) → 用 node vm 真的載入 art.js / core.js / game.js, 假 canvas(Proxy 吃掉所有方法、measureText / 漸層另外回最小物件)與假 document / Blob / rAF, 把驗證腳本逐幀輸入翻成 keydown / keyup, rAF 時間戳步階取 16.6667ms 讓每個 tick 剛好一步, 死亡後補 40 幀等換人延遲, 最後解析下載的 JSON 對帳; 另外加亂數按鍵跑幾萬 tick 看有沒有 console.error。測試末尾讀事件陣列卻是空的 → 過關 / 失敗時下載函式會清空事件陣列 → 在假 Blob 裡記下下載內容再對帳。單層、靠機關封路的關卡, 要逐代自查「被機關關住時走不走得到坑或尖刺」, 走不到就只能乾等逾時(GhostEchoV2 練哨關)。教學 / 提示類狀態機(依事件推進階段)的測試, 斷言「某階段出現」失敗 → 腳本在同一迴圈裡先按鍵再檢查, 但按鍵要下一個 tick 才被處理, 又多按一次把狀態推過頭 → 迴圈寫成「按鍵 → 跑 1 幀 → 檢查」; 直接跳關測試時先把前面關的未完成階段標成完成 / 略過, 否則「會帶到後面關卡」的階段會依編號優先蓋掉要測的階段; 每個「抓 / 送」等操作前先逐幀等到目標物件真的存在(批次之間會有空檔), 與目標無關的條件式提示預先標成已完成, 否則它們收起後立刻補位, 造成斷言誤報(捕泡手 v20); 同類: 送假 keydown 前先數音效, 計數永遠是 undefined → 聲音層規定「第一次輸入才初始化」, 沒送過按鍵就不播任何音效 → 測試開頭先用 `runInContext` 呼叫聲音層的初始化, 或先送一次按鍵再開始計數(DungeonZoo polish-8)
- 情境測試站在判定區邊緣按鍵, 預期的介面沒開, 後面斷言全部誤報 → 測試座標用手算距離, 恰好超出判定半徑 → 情境座標用遊戲自己的判定函式取點, 或取明確小於半徑的點, 不憑感覺擺在邊緣
