# SVG 撰寫規則

畫 SVG 前先讀完這份。目的是讓畫出來的圖能被 `svgtrace.py build` 正確轉成 PowerPoint 原生圖案, 而且轉進去之後群組分得有道理、使用者好選取好改。

## viewBox 換算

固定寫成:

```
viewBox="0 0 1184 <等比高>"
```

1184 是怎麼來的: 新建 16:9 檔可用寬度 12.333 吋 (13.333 吋整頁減兩邊各 0.5 吋邊界) x 96 (每吋像素數) = 1184。SVG 座標因此 1:1 對應 pptx 實際尺寸, `font-size` 直接寫數字就等於 pptx 裡的像素, 不會因為縮放而跑掉字級。

推算高度的步驟:

1. 先假設寬度吃滿 1184, 依原圖比例等比推出高度
2. 算出來的高度若超過 624 (= 6.5 吋 x 96, 也就是可用高度), 改成以高度吃滿 624 為準, 回推寬度 (寬度會小於 1184)

也就是說, `viewBox` 的第三個數字不一定是 1184, 只有寬度是限制因素時才是 1184; 高度是限制因素時第三個數字比 1184 小。

**這個 1184 是以「新建 16:9 檔」的可用寬度算出來的。** 如果 `build` 是追加進使用者一份既有的非 16:9 簡報, 腳本會依那份簡報實際的投影片尺寸等比縮放整個群組, 文字級數也會跟著等比改變 — 這是預期行為, 不必為了這種情況重算 viewBox。

## 支援的語法子集

轉換器認得這些標籤: `rect` `circle` `ellipse` `line` `polyline` `polygon` `path` `text` `tspan` `g`。

也支援: `marker` (畫箭頭)、`stroke-dasharray` (虛線)、線性漸層與放射漸層。

## 不支援

`foreignObject` 一定會被 `build` 的驗證階段擋下來, 連同其他任何轉換器不認得的標籤, 非零退出, 不產半成品。但清單**一次最多列 8 個**, 超過會註明還有幾個沒列出——修完列出的那幾個很可能還沒清乾淨, 要再跑一次 `build` 才知道。

另外**刻意不用**濾鏡效果與外部點陣圖 (`image` 嵌圖): 就算個別情況可能被驗證階段放行, 這兩者都不是「向量重畫」, 用了達不到臨摹的目的, 而且效果跟 PowerPoint 原生渲染落差大, 不如乾脆不畫。畫面上需要的陰影或材質感, 一律照下面「刻意簡化」那條處理。

也**刻意不用** `<style>` 區塊與 `class` 屬性設樣式: 顏色、外框等一律直接寫成元素上的 presentation attribute (`fill="..."` `stroke="..."` 之類), 不要靠 `<style>`/`class` 集中管理。驗證階段不會擋這兩者 (不是轉換器不認得的標籤, 不會出現在錯誤清單裡), Chrome 也會正確渲染出樣式, 但轉進 pptx 後樣式會整個掉光 (變成無填色加黑框)——這種落差在並排比對圖上看不出來, 自我校正迴圈也抓不到, 只有打開 pptx 才會發現。

## 分群慣例

用 `<g id="...">` 分群, 每一群在 pptx 裡會變成一個子群組, 群組內每個框、線、文字仍可個別點選編輯。

分群依**語意**, 不依畫的順序。例如一個「資料庫」圖示由圓柱形狀 + 標籤文字組成, 兩者要分在同一個 `<g id="database">` 裡; 不要因為文字是最後畫的就丟去跟別的東西同群。使用者拿到 pptx 之後要進 PowerPoint 整組搬動、整組換色, 分群分得有道理才選得順手。

## 文字

用 `text` 搭 `text-anchor` (`start` / `middle` / `end`) 對齊, 不要用空白或換行去排版位置, 那種對齊方式一放大字級就會跑掉。

`font-size` 直接寫數字 (例如 `font-size="24"`), 因為 viewBox 已經 1:1 對應像素, 這個數字等同轉進 pptx 後的字級大小。

多行文字**一律拆成多個 `<text>` 元素**, 每行各自設 `x` / `y` 對齊, 不要塞 `\n`。

`tspan` 只用在同一行**行內**的樣式變化 (例如一行裡有幾個字要換色), 不要拿 `tspan` 換行。實測用 `tspan` 換行轉進 pptx 後, 同一個文字框裡的多個 `tspan` 會變成同一段落底下的多個 run, PowerPoint 顯示時會把每行黏成一行 (例如「第一行第二行」擠在一起), 但 Chrome 渲染看起來完全正常——這種落差在並排比對圖上看不出來, 自我校正迴圈也抓不到, 只有打開 pptx 才會發現。拆成獨立的 `<text>` 元素還有額外好處: 轉進 pptx 後每行是各自獨立、可以分別搬移編輯的文字框, 更符合「圖層乾淨」的目標。

## 圖案數預算

**整張圖控制在 60 個形狀以內, 超過就是畫太細了。** `build` 跑完會印出實際圖案數, 對照這個預算檢查。

這條不是美學偏好, 是硬性限制: 使用者要在 PowerPoint 裡點選、搬動、換色, 形狀一多選取窗格就變成一長串無名清單, 點也點不到想要的那個, 整份東西就失去意義了。上千個形狀的檔案還會讓 PowerPoint 明顯變鈍。

超過預算時的處理順序:

1. 把同色、相鄰、語意上屬於同一件事的碎形狀合併成一個 `path`
2. 砍掉原圖有但不影響辨識的細節 (碎陰影、材質雜點、極小的裝飾)
3. 把複雜輪廓用更少的貝茲曲線重畫, 不要用幾十段短直線拼

**絕對不要**為了更像原圖而逐像素或逐色塊鋪形狀。那種做法在並排比對圖上很漂亮, 但交付的 pptx 完全不能編輯, 等於沒達成這個 skill 的目的。

## 刻意簡化

臨摹的目標是「結構正確、圖層乾淨」, 不是「像素級相似」。以下一律不畫, 遇到原圖有也直接省略, 不要為了像而硬湊語法:

- 陰影
- 雜訊或材質貼圖
- 手繪風格的抖動線條

複雜漸層 (三色以上、多個 stop) 一律退成單色, 或最多退成兩段的線性/放射漸層。理由一致: 使用者要的是進 PowerPoint 之後能換文字、換配色、搬框線, 這些精緻但不可編輯的視覺效果只會擋路, 沒有換到任何好處。
