# 階段 4 頁面內容: 講稿怎麼變成頁面

**開始擬任何一頁之前先讀完這份。** 這裡決定的是「投影片上放什麼」, 而不是「怎麼排版」。

最常見的失敗是把講稿換個排版貼上去 — 條列一對一搬過去, 看起來做完了, 實際上產出的是一份「講者會照著唸的稿」。下面四條理念就是為了擋掉這件事。

## 1. 四條理念

**(1) 講稿與簡報是兩種東西, 不是同一份內容的兩個副本**

- 講稿是**演講者講的**: 從簡報延伸, 要具體且完整
- 簡報是**觀眾看的**: 只呈現抽象輪廓且簡短, 讓觀眾知道現在的題目即可
- 最忌諱演講者照著簡報唸稿

判準: 投影片的字是給聽眾的**錨點** (走神回來接得上現在講到哪), 講者的話才是展開與論證。東西從投影片上拿掉不等於不講, 只是改成只有嘴巴講。

**(2) 濃縮講稿最好的方法是圖像, 而且要是可以拿來比喻的圖像**

優先序: **幽默 > 精準 > 無圖**。

- 先問「這頁能不能變成一張圖」
- 能圖像化但只想得到精準版 (流程圖、鏈條圖) 時, 先試著換成有梗的比喻; 換不到才留精準版
- 真的很難圖像化, 才改成一句最簡短的話

**(3) 例外: 具體數據、表格、不可含糊帶過的技術細節不在此限**

該講清楚就講清楚。功能名、版本號、副作用、玩法對照表這類東西, 密度高是對的。

同一份簡報裡不同 topic 的密度可以差很多 — 講協作方式的 topic 可以一頁一句話配一張圖, 講引擎功能的 topic 就該把版本號與副作用寫清楚。**不要為了視覺一致而犧牲該講清楚的內容。**

**(4) 切頁看內容量, 不看配時**

第一刀切在講稿的每個標題; 切完看這頁擠不擠, 太龐大就再細切。**不要用「一頁 N 秒」去回推頁數** — 那會讓內容遷就數字。

## 2. 決策順序

對每一個講稿章節:

1. 這段的**核心是哪一句**? 那句就是頁標題
2. 這句能不能變成一張圖? 能 → 寫圖片描述, 標題那句留著, 其他全部交給嘴巴
3. 不能 → 這段是不是第 3 條的例外 (數據 / 表格 / 技術細節)? 是 → 用 `table` / `cards` / `compare` 把它講清楚
4. 都不是 → 只留最簡短的一句話

## 3. 不該上投影片的東西

- **笑點**。印出來聽眾會先讀完, 講出來就沒效果了 — 笑點一律留給嘴巴
- **論證過程**。投影片放結論, 推導過程用講的
- **同一件事說兩遍**。若欄小標已經在講白話效果, 主標就不要再寫一次效果句 — 主標改成只說這頁屬於哪一塊
- **配時、對應講稿第幾段、為什麼這樣切**。這些是 meta, 寫 STATUS.md 的 log, 不要寫進 SLIDES.md (見 `formats.md`)

## 4. 標題的兩層

一頁通常有兩層標題:

- **章節標籤** (role `label`, 慣例左上角小字): `案例2` / `小結` 這類。**這種標題不能省** — 少了它聽眾不知道現在在哪個段落
- **頁標題** (role `title`): 這頁要講的那句話

但也**不要為了一個章節標籤獨立開一頁**。標籤放進該段第一頁的左上角就好, 給它整頁的視覺比重太浪費 — `section` 版型留給 topic 層級的分隔, 不要用在 topic 內的小段落。

## 5. 圖片的三種來源, 在這個階段就標

寫圖片描述時在描述開頭標來源, 後續階段才知道各自要怎麼處理:

- `@photo` 使用者提供的圖片或照片 → build 前要檢查 EXIF 轉向與透視 (見 `photo-dewarp.md`)
- `@ai` 較複雜、非簡單示意圖, 需 AI 生圖 → 要寫 prompt
- `@svg` 較簡單的示意圖, 可向量畫 → 由 AI 寫 SVG, **但要等 STYLE.md 定案後才畫** (viewBox 尺寸要照版型的 box 英吋算)

比喻圖的描述寫成兩段: **意象** (這張圖要表達什麼) + **呈現** (畫面上實際有什麼)。不要寫「幽默點在哪」, 那是寫給自己看的。

## 完成條件

全部 topic 的「頁面內容」欄轉 `done`, 且每一頁都通過這個檢查: **把投影片上的字唸一遍, 聽起來不像一段完整的話** — 像的話就是講稿搬過來了。
