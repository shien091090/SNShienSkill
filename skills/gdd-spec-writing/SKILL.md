# GDD 規格書撰寫流程

這個 skill 處理的是一種很特定的協作情境：企畫已經寫了一半的 GDD，剩下的部分不是「文字沒打完」，而是**設計決策還沒做**。所以核心不是代筆，是**先把決策逼出來，再照既有格式落成文件**。

寫規格書最大的失敗模式是：模型讀了一半文件就開始寫，把沒定的東西用漂亮的句子糊過去，產出一份讀起來很完整、但每個數字都是編的規格。企畫看了會以為決策做完了，實作照著做，等到平衡測試才爆炸。這個流程的每一步都是在防這件事。

## 流程總覽

1. **全 vault 盤點** — 讀完所有規格，產出完成度地圖與矛盾清單
2. **確認優先順序** — 讓使用者決定本輪攻哪一份
3. **多輪問答** — 把設計分岔攤成具體選項，逐輪收斂
4. **依既有模板成稿** — 產出草稿交審
5. **修訂與存檔** — 改到滿意才寫回 vault，連動修改另外徵求同意

不要跳步。特別是不要在盤點完成前就開始問問題——問到文件裡已經寫過的東西，是最快失去使用者信任的方式。

## 第一步：全 vault 盤點

先跑打包的稽核腳本拿到骨架，再實際讀檔補上判斷：

```bash
python3 scripts/audit_vault.py <vault路徑>
```

腳本會回報斷掉的 wikilink、孤兒檔、空檔、以及帶有佔位符（`待定`、`TBD`、`{數值}`、`X`）的段落。這些是機械可驗證的部分。

腳本抓不到、必須靠閱讀判斷的部分：

- **哪些檔案是半成品** — 章節斷在一半、只有質化描述沒有數值表、標題承諾了但內文沒寫（例如檔名叫「魔物行為與戰鬥」但完全沒有戰鬥數值）
- **跨文件矛盾** — 同一件事在兩份文件講法不同。這是最有價值的產出，因為企畫自己往往看不到（他是分次寫的）
- **名詞不統一** — 同一個東西三個名字，或同一個名字指兩個東西
- **格式慣例** — 這份 vault 的規格書長什麼樣（見 `references/format-conventions.md` 的歸納方法）

如果 vault 很大，用 subagent 平行讀，讓它回傳結構化摘要而不是原文，省 context。

盤點結果要**分組呈現**給使用者，不要流水帳。有效的分組方式：已被連結但是空檔 / 被連結但檔案不存在 / 索引列了但連結都還沒建 / 半成品缺數值。最後單獨列出「會擋住後續的全域矛盾」——那些不先定就會讓每一份新規格繼續分歧的東西（貨幣體系、資源可不可以減少、分類列表到底有幾種）。

## 第二步：確認優先順序

盤點完就停下來讓使用者選。可以推薦（通常「先定全域基準」最划算，因為便宜又解鎖全部），但不要替他決定——企畫對哪份最急有自己的判斷，可能牽涉到美術或程式的排程。

同時確認交付方式：直接寫回 vault，還是先給草稿審過再存。

## 第三步：多輪問答（這步是重點）

每輪問 3~4 個**結構性分岔**，不要問細節。分岔的判準是：這題答案不同，後面整份規格的骨架就不同。細節（欄位順序、Tooltip 文案、排序預設值）自己推，寫進草稿讓使用者在審稿時修就好——那比在問答階段耗他的注意力有效率得多。

**每個選項都要附代價。** 不是「A 下拉選單 / B 小地圖 / C 回場景點」，而是每個選項講清楚它換來什麼、要付什麼（要不要新寫一套系統、會不會跟現有規格打架、實作量差多少）。使用者是在做工程排程決策，不是在挑口味。

### 分清楚「規格說的」和「你提的」

這點極其重要，而且很容易搞砸。當使用者問「這段是哪來的」，你必須能立刻分辨：

- **規格原文有的** — 引用出處與原句，一字不改
- **你在前面幾輪提議、使用者選了的** — 明說是你提的，不要事後包裝成規格既有內容
- **你正要提議的** — 明說還沒定

真實案例：前一輪我提了「面板內下拉選單」當選項，使用者選了，兩輪後他問「下拉選單是哪個規格寫的？」——正確答案是「不是規格寫的，是我提的、你選的」。原始規格只寫了「透過員工管理面板設定崗位」，完全沒提 UI 型態。如果含混帶過，使用者會以為自己在遵循舊決策，實際上是在遵循模型的即興發揮。

### 抓出「有名字但沒定義」的名詞

規格裡常有一句話隨手寫下一個名詞，之後全 vault 再也沒有定義它。例如「指派維護員預設區域」——但整份 GDD 從來沒有「區域」這個概念，只有「展區」有編號有邊界。

這種名詞是設計債。發現時要當面攤開：問使用者當初寫這個詞時心裡想的是什麼，並提供「認真做出這個概念」與「降級成現有概念」兩種收法。如果選了降級，順手提議把原文用詞也改掉，不要留一個不存在的概念在文件裡。

### 主動指出選擇的副作用

使用者做完選擇後，花點力氣推演這組選擇會產生什麼支配性策略或死角。例如「應徵者屬性隨機、靠薪資分流」＋「升級後薪資不漲」＋「工作會自動升級」＝ 最優解永遠是只雇最便宜的然後養起來，薪資分流機制形同虛設。

發現這種事要講，並提出處理方式，但**不要因此擋住流程**——講完、給預設解、繼續寫，讓使用者在審稿時決定要不要換槓桿。

### 工具失敗時的退路

如果多選題工具送不出去（長中文內容偶爾會有編碼問題），直接改用純文字列問題、請使用者回編號。不要卡在工具上重試三次，那只是浪費使用者的時間。

## 第四步：依既有模板成稿

寫之前先讀 `references/format-conventions.md`，並實際打開 vault 裡**兩三份最相近的既有規格**當範本——同類型的頁面（管理介面找管理介面、系統機制找系統機制）比通則更可靠。

撰寫時的幾個原則：

**沒定的東西要看得出來沒定。** 需要平衡測試才能定的數值，給一組合理暫定值並標註「（暫定，待平衡測試調整）」；有風險的設計假設，用引言區塊標 `⚠ 平衡待驗證`，寫清楚在什麼條件下會失效、失效時的調整槓桿依序是什麼。這比留一個空白的 `{數值}` 有用得多，因為它讓實作可以先跑起來，同時保留了決策軌跡。

**把懸空的引用接上。** 如果這份規格提到的某個東西（建築、系統、頁面）在 vault 裡從沒定義過，而它又是本規格運作的前提，就在本規格裡開一節把它定義清楚，並在關聯規格區列出它應該歸屬的母文件。不要假裝它存在。

**結尾放「關聯規格」區。** 列出本規格依賴哪些文件、以及哪些文件應該反過來指向它。這是下一輪盤點的輸入。

## 第五步：修訂與存檔

草稿交出去時，主動點名**需要使用者特別過目的地方**：你自己補上去的東西、關鍵公式與係數、你自己判斷的防呆嚴苛程度、以及跟其他規格有互動的規則。使用者的注意力有限，你要幫他分配。

修訂時完全照使用者指示，不要夾帶。但如果同一個問題在別處也存在（例如他要求某欄位改顯示格式，而另一個職業的同一份清單也有同樣的可讀性問題），可以延伸處理並在回報時明說延伸了什麼、為什麼。

**連動修改另外徵求同意。** 修正別的檔案裡的死連結、統一用詞——這些都對，但它們動到使用者既有的檔案，要單獨列出來等他點頭，不要順手改掉。

存檔後如果 vault 有 git，依照 repo 既有的 commit message 慣例給出指令（讀 `git log --oneline` 或 `.git/logs/HEAD` 看慣例），不要自作主張換風格。

## 收尾

一輪結束後，回報本輪產出、還沒執行的連動修改、以及下一份的建議順序（哪份材料最齊、哪份跟剛寫完的最相關）。讓使用者能無縫接下一輪。
