# LINE 群組訊息匯出自動化

## 觸發詞：line日報

當使用者說「line日報」時，先判斷這次要跑的範圍：

- **預設（訊息裡沒有額外指示，或明確要求「都要」「完整」）**：匯出 + 彙整都跑，即 Step 0~3 全部執行完後，接續執行 `line-group-daily-report` skill。
- **使用者額外指示只要匯出**（例如「line日報，只匯出」「line日報，先不要彙整」「line日報，不用出摘要」）：只執行 Step 0~3，**不**接續執行 `line-group-daily-report`。
- **使用者額外指示只要彙整**（例如「line日報，只彙整」「line日報，不用重新匯出」「line日報，直接彙整就好」）：**跳過 Step 0~3**，直接執行 `line-group-daily-report` skill 的完整流程（比照該 skill 原本「讀取現有匯出檔並輸出摘要」的行為，適合已經匯出過、只是想重新彙整的情境）。

以下 Step 0~3 只在「預設」或「只要匯出」這兩種情境下需要執行（**全程自動執行，不需使用者確認**，任一群組失敗則跳過並記錄，不中斷整體流程）：

前提：LINE 桌面版已登入且在背景執行。所有 PowerShell 指令開頭都要先執行：
```powershell
. "C:\Users\lithoshu\.claude\skills\line-group-export\LineExportHelper.ps1"
```

**重要**：LINE 的所有畫面（主視窗、聊天室、「另存新檔」對話框、「是否覆蓋」對話框）都是 LINE 自己畫的介面，沒有串接 Windows UI Automation（掃描不到任何按鈕/選單元件、也讀不到清單項目的名稱），所以不使用 `Invoke-DialogButtonClick`（該函式僅適用於真正的原生 Windows 對話框，例如 Notepad 的開啟舊檔）。找「自動化」tab 與讀取群組清單（Step 1）需要「截圖 → Read 工具視覺判讀座標 → `Invoke-MouseClick`」，因為這部分內容每次都會變（群組名稱、清單順序）；但 Step 2 裡開啟聊天室之後的每一步（選單、存檔、覆蓋確認、關閉）已校準出穩定的座標偏移量，直接算座標盲點即可，不用每步都截圖確認（見 Step 2 開頭的偏移量清單）。

**Step 2 開啟聊天室一律走搜尋框，不再點清單裡的群組座標（2026-08-08 設計、2026-08-10 實測失敗一次、使用者指示繼續採用並修正）**：「自動化」清單是依最近訊息排序的動態清單，Step 1 截圖判讀座標到 Step 2 實際點擊之間有數秒延遲（截圖、視覺判讀），這段時間內若有任何群組收到新訊息，清單順序就會變、點擊座標就可能點到別的群組或已處理過的群組（2026-08-07 實測連續遇到 3 次）。搜尋框本身位置固定、不受清單重排影響，用它直接搜出目標群組再開啟，可以把「清單目前排序」這個不穩定因素整個從迴圈裡拿掉。

**2026-08-10 實測失敗記錄**：第一次真正嘗試搜尋框做法時，點擊搜尋框座標 → `Ctrl+A` → `{DEL}` → `Set-Clipboard` → `Ctrl+V` 之後截圖確認，搜尋框內**完全是空的**（只有預留的放大鏡圖示與一個常駐的清除「x」小圖示，看不出任何貼上的文字），導致清單完全沒有被過濾，只好整段退回舊的「截圖判讀清單座標」做法（見下方第 1 步的備援）。使用者事後檢視畫面時另外注意到搜尋框「有一堆空白」，懷疑是清空/貼上時機出錯或點擊座標本身沒有真正落在輸入框上。**使用者指示：下次繼續使用搜尋框做法**，並在每次搜尋前先確實清空搜尋框（見下方第 1 步的加強做法），若清單排序真的因此穩定下來，Step 2 每輪重新截圖確認清單順序（見第 9 步說明）就不再需要。

**群組名稱一律用 `Open-LineChatWindow` 現場取得，不要事先假設**：LINE 清單面板會把過長的群組名稱截斷顯示（例如「台中 媽媽寶寶/二手商品出清/贈...」），但聊天視窗的真實標題永遠是完整名稱。`Open-LineChatWindow`（在 `LineExportHelper.ps1` 裡）會雙擊清單座標、比對點擊前後該程序的頂層視窗清單抓出新開的那個視窗，回傳其正確 `Handle`/`Title`（完整、含 emoji）/`Left`/`Top`/`Right`/`Bottom`。這比「先讀 Step 1 截圖裡的截斷名稱、再用 `Find-WindowByExactTitle` 精準比對」更可靠，也不需要為了看到完整名稱而放大 LINE 視窗。所有後續步驟（選單偏移量、存檔檔名、關閉按鈕）都直接用這個回傳物件，不用另外呼叫 `Find-WindowByExactTitle`。

### Step 0 — 校準視窗

LINE 常同時開著多個聊天室視窗（每個聊天室是獨立的頂層視窗），`Find-AppWindow -ProcessName "LINE"`（用 `Get-Process` 的 `MainWindowHandle`）不保證抓到主視窗，可能抓到某個聊天室視窗。改用 `Find-WindowByExactTitle` 精準比對標題為「LINE」的那個主視窗：

```powershell
$window = Find-WindowByExactTitle -Title "LINE" -TimeoutSeconds 10
if (-not $window) { throw "找不到 LINE 主視窗，請確認 LINE 已啟動" }
Show-AppWindow -Handle $window.Handle
```
記下 `$window.Left/Top/Right/Bottom/Width/Height`，之後點擊座標一律用「相對這個 rect 的偏移量」計算，而非寫死的螢幕絕對座標。

### Step 2 — 逐一處理群組（迴圈直到 `$pendingGroups` 全部處理過）

**重要背景（2026-07-07 實測發現，2026-07-17 修正等待時間與完成偵測邏輯）**：
- 開啟群組聊天室**需要雙擊**（連續呼叫兩次 `Invoke-MouseClick`，間隔約 120ms），單擊沒有反應。`Open-LineChatWindow -X <x> -Y <y>` 已經封裝好「雙擊 + 用視窗清單 diff 找出新開的聊天視窗」，直接呼叫它，不用自己重寫這段。
- LINE 每個聊天室是獨立的頂層視窗，使用者桌面上可能同時疊著好幾個其他聊天室視窗（互不相關的舊視窗，甚至包含不少標題為空字串、`IsWindowVisible` 卻是 true 的殘留視窗）。這也是為什麼用「diff 找新視窗」比「假設座標」或「假設群組名稱」可靠。
- **開啟聊天室後一律先最大化視窗，再操作「...」與「儲存聊天」（2026-07-22 使用者指定採用）**：聊天室視窗剛開啟時的大小/位置每次重開機、每次執行都可能不一樣，若直接對「非最大化視窗」算相對偏移量，長期下來容易因為視窗初始位置飄移而失準、要重新校準。改成「先最大化」之後，視窗一定會填滿它所在的那個螢幕（本機是 3840x1080 雙螢幕併成的虛擬桌面，LINE 主視窗與聊天室都開在左側螢幕，最大化後 rect 穩定落在 `Left=-8, Top=-8, Right=1928, Bottom=1040` 附近），「...」與「儲存聊天」的**絕對螢幕座標**因此也跟著固定，不會再受每次視窗初始位置不同影響。
  - **最大化用 `Send-MaximizeShortcut -Handle $chat.Handle` 送出 Win+上快捷鍵，不要點擊放大鈕（2026-08-08 起改用，2026-08-07 實測驗證過一次）**：原本的做法要先算「相對最大化前聊天視窗 rect 的偏移量 `(Right - 45, Top + 18)`」才能點到放大鈕，這是當時唯一還在依賴「非最大化視窗座標」的一步，也是視窗初始位置飄移時最容易失準的地方。改送鍵盤快捷鍵完全跳過這個座標計算，且與滑鼠點擊得到的最大化結果一致（實測最大化後 rect 落在同一組 `(-8,-8,1928,1040)`），下面的選單/儲存聊天偏移量不受影響、不用重新校準。呼叫後等待約 400-600ms 讓最大化動畫完成，然後用 `Get-ProcessWindows -ProcessName "LINE"` 依 `Handle` 重新取得該視窗**最大化後**的新 rect（這只是輕量 Win32 呼叫，不是截圖，成本很低，直接呼叫即可，不用每次額外截圖確認）覆蓋 `$chat`。
  - 最大化後，「...」選單按鈕相對**新 rect** 的偏移量是 `(ChatWindow.Right - 29, ChatWindow.Top + 66)`（2026-07-22 實測校準，與非最大化狀態的偏移量不同，不能沿用舊公式）。
  - 「儲存聊天」選單項：以最大化後「...」的點擊座標 `(menuX, menuY)` 為基準，偏移量是 `(menuX - 49, menuY + 270)`（2026-07-22 實測校準，同樣與非最大化狀態不同）。
  - **只要本次執行的第一個群組成功驗證過一次上述座標，同一次執行（同一個 PowerShell session 期間）後續群組直接沿用同一組計算公式即可，不需要每個群組都重新截圖驗證**——因為最大化後 rect 是同一個螢幕、同一個尺寸，理論上每次都會落在同樣的絕對座標。若中途發現點擊持續落空（例如螢幕解析度、視窗排列被使用者手動改變），才需要重新截圖校準。
- **重大發現：「另存新檔」對話框記住的資料夾可能是錯的（2026-07-22 實測發現）**：測試時「儲存聊天」點下去，對話框直接開在完全無關的路徑（`D:\Git\yile_line_material\尚未整理`），而不是預期的 `D:\倉庫\其他\Line社群訊息紀錄`。原因不明（可能是使用者或其他程式最近手動存過檔到別處，LINE 記住了那個路徑），但如果照原本邏輯盲點固定座標的「存檔(S)」按鈕，會把聊天記錄存到完全錯誤的資料夾，且因為 `Wait-FileStable` 檢查的是預期路徑下的檔案，會一直等不到，只會被記錄成失敗，不會誤存成功但事後很難發現檔案存去哪了。**修正做法：不要盲點「存檔(S)」，改成每次都明確指定完整路徑**，見下方 Step 4-5 的新做法。
- 其餘按鈕偏移量（「...」與「儲存聊天」已改為最大化後的版本，見上一點）：
  - 「確認另存新檔」（覆蓋確認）對話框「是(Y)」按鈕：固定螢幕座標 `(1013, 520)`（此對話框位置不跟聊天視窗走，經測是固定的；**2026-08-10 起這個按鈕預設不用點**，只有同一天重複執行、資料夾內已有同名舊檔的情境才需要，見下方 Step 6 的例外說明）
  - 右上角「X」關閉按鈕：相對**最大化後**的 rect，`(ChatWindow.Right - 14, ChatWindow.Top + 12)`
  - 若之後發現這些座標開始失準（例如 LINE 版本更新、視窗配置改變、螢幕排列被使用者調整），回頭用截圖裁切確認新的偏移量，並更新這份文件。
- **等待時間務必抓夠（2026-07-17 教訓）**：一開始用 700ms 等「另存新檔」對話框跳出，在群組數量一多、系統負載變高時常常等不到，點擊落空又不知道，導致「另存新檔」對話框卡在畫面上、下一個群組的雙擊點擊誤打在卡住的對話框上，接著整批處理雪崩式失敗（且下一節說的完成偵測舊邏輯還會把這種失敗誤報成功）。**改用「儲存聊天」點擊後等 1000-1300ms 再貼上路徑送出**，寧可等久一點，不要抓 700ms。送出（`{ENTER}`）之後則不用再等對話框反應——2026-08-10 起改成固定等 1000ms 就直接關閉聊天室，見下方 Step 5-6。
- **完成偵測務必比對時間戳記，不能只看「檔案穩定」（2026-07-17 教訓）**：如果該群組今天稍早已經匯出過、這次卻因為對話框卡住而存檔失敗，舊檔案會維持完全不變 —— 而「連續 3 次輪詢，檔案大小與時間都沒變」這個穩定條件，對一個「本來就沒被動過」的舊檔案幾乎立刻就會成立，造成明明存檔失敗、`Wait-FileStable` 卻回報成功的假陽性。**呼叫 `Wait-FileStable` 前先記下 `$startTime = Get-Date`，呼叫時一定要帶 `-Since $startTime`**，這樣舊檔案不會被誤判為剛存好。
- **檔名比對眉角**：LINE 存檔時，群組名稱裡的 `/ \ : * ? " < > |` 等 Windows 檔名不允許字元會被直接移除（不是取代成其他符號、也不會補空格）；名稱過長時，LINE 也會把整個檔名靜默截斷（不會有任何錯誤提示）。組出預期檔名前先用 `-replace '[\\/:*?"<>|]', ''` 清掉不合法字元；如果 `Wait-FileStable` 一直等不到，且該群組名稱很長，很可能是截斷造成的檔名不符，可用「資料夾裡 `LastWriteTime -ge $startTime` 的檔案」代替精確檔名比對來確認匯出結果。

5. **不要盲點「存檔(S)」按鈕**（對話框開啟時記住的資料夾可能不是預期的匯出資料夾，見上方說明）。改用清空 + 剪貼簿貼上完整路徑，同時完成「換資料夾」與「送出存檔」兩件事：
   ```powershell
   Add-Type -AssemblyName System.Windows.Forms
   [System.Windows.Forms.SendKeys]::SendWait("^a")
   Start-Sleep -Milliseconds 200
   [System.Windows.Forms.SendKeys]::SendWait("{DEL}")
   Start-Sleep -Milliseconds 200
   $sanitized = $chat.Title -replace '[\\/:*?"<>|]', ''
   $fullPath = Join-Path "D:\倉庫\其他\Line社群訊息紀錄" "[LINE]$sanitized.txt"
   Set-Clipboard -Value $fullPath
   Start-Sleep -Milliseconds 200
   [System.Windows.Forms.SendKeys]::SendWait("^v")
   Start-Sleep -Milliseconds 300
   [System.Windows.Forms.SendKeys]::SendWait("{ENTER}")
   ```
   注意：**不要用 `SendKeys` 直接打中文路徑字串**（例如逐字 `SendWait($fullPath)`）——實測會因輸入法/多國語言鍵盤問題把中文字元和 `.txt` 副檔名打成亂碼（例如變成無關的 CJK 部首字元）。務必先 `Set-Clipboard` 再 `^v` 貼上。**貼上後務必再明確送出一次 `{ENTER}` 才會真的送出存檔**（2026-07-22 實測：曾經以為 `Set-Clipboard` 帶的字串結尾換行會等同自動按下 Enter 直接送出，但同一天稍後測試發現貼上後對話框其實原封不動停在畫面上、完全沒有送出，直到補按 `{ENTER}` 才真正觸發存檔/跳出覆蓋確認——不可靠，每次都要明確按 `{ENTER}`)。
   送出後**只等待約 1000ms**，不管畫面此時是「另存新檔」對話框已消失、跳出覆蓋確認、跑存檔進度、還是跳出「無法下載項目」錯誤彈窗，**都直接進入下一步關閉聊天室，不需要判斷畫面上是哪種狀態、也不需要點任何按鈕**（2026-08-10 使用者確認並指示採用：按下 Enter 送出存檔後，實際存檔動作已經在背景進行，即使畫面上還停著覆蓋確認、進度條或錯誤彈窗，直接關閉聊天室視窗也不影響背景的存檔或已寫入的檔案；這個做法同時免除了舊版需要精準點擊「是(Y)」覆蓋確認、判斷「下載完畢」小視窗座標、以及對「無法下載項目」錯誤彈窗特殊處理這三段最容易卡住、最花時間的邏輯）。
6. 用 `$chat.Right`/`$chat.Top` 依偏移量 `(Right - 14, Top + 12)` 計算右上角「X」關閉按鈕座標 → `Invoke-MouseClick` 關閉聊天室。
   - **例外／已知限制**：這個簡化流程假設匯出資料夾在每次執行開始時是空的（`line-group-daily-report` skill 的最後一步會清空資料夾），所以正常情況下不會跳出「確認另存新檔」覆蓋確認對話框。若同一天內重複執行匯出（資料夾內已有同名舊檔），覆蓋確認對話框需要明確點「是(Y)」才會真的覆蓋，直接關閉視窗可能讓這次存檔停在確認畫面、實際沒有覆蓋成功——這種情境下才需要回頭用舊版做法：點擊固定座標 `(1013, 520)`（同一天測試發現這個座標會在 `(1006,524)`~`(1045,524)` 之間跳動，落空時改截圖找「是(Y)」實際位置），且**絕對不要靠按 `{ENTER}`** 確認覆蓋（這個對話框有時候預設 focus 在「否(N)」上）。
7. 完成偵測（在關閉聊天室之後才做，因為存檔是背景動作，不需要等聊天室還開著）：
   ```powershell
   $sanitized = $chat.Title -replace '[\\/:*?"<>|]', ''
   $targetFile = Join-Path "D:\倉庫\其他\Line社群訊息紀錄" "[LINE]$sanitized.txt"
   $stable = Wait-FileStable -Path $targetFile -StableChecks 3 -IntervalMilliseconds 700 -TimeoutSeconds 45 -Since $startTime
   ```
   若 `$stable` 為 `$false`，記錄失敗（註明是逾時、檔名可能被截斷，或跳出過「無法下載項目」代表 LINE 本身存檔失敗），先不要急著判定「這群組完全沒存到」——可以額外檢查資料夾裡有沒有 `LastWriteTime -ge $startTime` 的新檔案，若有就視為成功、並在記錄裡標註實際檔名。
8. 標記該群組完成：
   ```powershell
   Write-ExportLog -LogFolder "C:\Users\lithoshu\.claude\skills\line-group-export\logs" -Message "群組 [$($chat.Title)] 匯出成功"
   ```
9. 回到迴圈頂端，取 `$pendingGroups` 中下一個尚未標記完成的群組名稱，重複第 1 步用搜尋框開啟；全部處理完後結束迴圈。搜尋框做法**理論上**不需要每輪重新截圖判讀清單順序——這正是這個改動要解決的問題：舊做法每輪都要截圖判讀「群組目前在清單裡的座標」，但清單排序會隨最新訊息即時變動，判讀當下的座標到實際點擊之間如果剛好有新訊息進來，就會點錯群組（2026-08-07 實測連續發生 3 次）。但截至 2026-08-10 搜尋框做法還沒有連續驗證成功過（見上方 Step 2 開頭的失敗記錄），**在搜尋框做法確認能穩定把文字貼進搜尋框、篩出正確群組之前，先維持每輪重新截圖確認清單目前排序＋座標的舊做法，兩者並用比較保險**；等連續一次執行全程搜尋框都正常運作，才把這步驟拿掉。

**卡住的對話框如何復原**：如果某一輪點擊順序中，等待時間仍然不夠、或畫面被別的視窗（例如剛好彈出的下載完成提示、被使用者切到最大化的其他聊天視窗）蓋住，「另存新檔」與「確認另存新檔」對話框會卡在畫面上不消失，且會擋住後續所有點擊（下一個群組的雙擊可能誤點在卡住的對話框上，導致 `Open-LineChatWindow` 找不到新視窗、回傳 `$null`）。徵兆：連續兩個以上群組的 `Open-LineChatWindow` 都回傳 `$null`，或某群組的完成偵測明明該群組先前沒問題卻突然大幅逾時。復原步驟：
1. 截圖確認目前畫面上是否有對話框或非預期的最大化視窗擋住畫面
2. 若有其他視窗被最大化蓋住，先用 `Show-AppWindow` 把該卡住流程的聊天視窗（或用 Step 0 存下的 `$window.Handle` 把 LINE 主視窗）拉回最上層
3. 找到「確認另存新檔」的「是(Y)」或「另存新檔」的「存檔(S)」按鈕實際座標（此時建議截圖確認一次，不要盲點），依序點掉，直到畫面乾淨
4. 用 `Close-AppWindowByHandle -Handle <handle>` 關閉處理到一半、狀態不明的聊天視窗（這個函式用 `PostMessage(WM_CLOSE)`，不需要視窗在最上層或座標可見，比點擊 X 更可靠）
5. 重新截圖確認清單狀態後，從卡住的那個群組重新開始處理

**另一種卡住殘留：獨立的「Line社群訊息紀錄」檔案總管視窗（2026-07-22 實測發現）**：偶爾會在畫面上多出一個標題就叫「Line社群訊息紀錄」的視窗（有完整的檔案總管工具列、側欄），蓋住 LINE 視窗，導致下一個群組的雙擊點空。徵兆與上面「卡住的對話框」相同（`Open-LineChatWindow` 連續回傳 `$null`）。這個視窗不是聊天室視窗，抓不到 `Get-ProcessWindows -ProcessName "LINE"`，要用標題比對關掉：
```powershell
Add-Type @"
using System; using System.Runtime.InteropServices; using System.Text;
public class ExplorerFind {
    public delegate bool EnumWindowsProc(IntPtr hWnd, IntPtr lParam);
    [DllImport("user32.dll")] public static extern bool EnumWindows(EnumWindowsProc lpEnumFunc, IntPtr lParam);
    [DllImport("user32.dll", CharSet = CharSet.Unicode)] public static extern int GetWindowText(IntPtr hWnd, StringBuilder text, int count);
    [DllImport("user32.dll")] public static extern bool PostMessage(IntPtr hWnd, uint Msg, IntPtr wParam, IntPtr lParam);
}
"@
$found = @()
[ExplorerFind]::EnumWindows({ param($hWnd, $lParam)
    $sb = New-Object System.Text.StringBuilder 256
    [ExplorerFind]::GetWindowText($hWnd, $sb, 256) | Out-Null
    if ($sb.ToString() -like "*Line社群訊息紀錄*") { $script:found += $hWnd }
    return $true }, [IntPtr]::Zero)
foreach ($h in $found) { [ExplorerFind]::PostMessage($h, 0x0010, [IntPtr]::Zero, [IntPtr]::Zero) | Out-Null }
```

**點「儲存聊天」後跳出「無法下載項目。」錯誤彈窗（2026-08-04 實測發現，2026-08-10 起不再需要特殊處理）**：某些群組送出存檔後，不會靜靜存檔完成，而是跳出一個小彈窗顯示「無法下載項目。」+ 一個「確定」按鈕，代表 LINE 本身存檔失敗（非座標點擊問題）。舊版曾經想點掉這個彈窗的「確定」按鈕，但實測發現**點擊經常沒有反應**（截圖、精算按鈕中心點座標、多次重新嘗試都點不掉，`{ENTER}` 按鍵也無效，`Get-Process` 顯示程序仍是 `Responding=True` 並非真的整個卡死），也曾經需要改用點擊視窗標題列「X」（`Right-14, Top+12`）並搭配 Alt+F4 才勉強關掉，過程很花時間。

**2026-08-10 起不用再處理這個彈窗**：因為 Step 5 送出存檔後固定只等 1000ms 就直接關閉聊天室（不管畫面顯示什麼狀態），這個彈窗本來就不會擋路，直接被連同聊天室一起關掉即可，不需要特別偵測它有沒有出現、也不需要點「確定」。這個群組最終算成功還是失敗，交給 Step 7 的完成偵測（`Wait-FileStable`／檢查 `LastWriteTime`）判斷即可——偵測不到新檔案就記錄失敗，理由寫「可能跳出無法下載項目或存檔逾時」。

**執行時偶爾出現的無關錯誤「Remove-Item on system path '/' is blocked」（2026-07-22 實測發現，原因未明）**：把「開啟聊天室 → 最大化 → 點選單 → 點儲存聊天 → 清空欄位貼上路徑 → 送出 → 確認覆蓋 → 完成偵測 → 關閉 → 記錄」全部串成一個很長的 PowerShell 指令一次執行時，偶爾會在指令真正執行前就被擋下、回報這個跟腳本內容完全無關的錯誤（腳本裡並沒有呼叫 `Remove-Item`），且該次呼叫完全沒有執行（聊天室視窗都沒開啟）。目前找不到明確觸發條件，但**拆成 2-3 段分別執行**（例如「開啟+最大化+點選單+點儲存」一段、「清空+貼路徑+送出」一段、「確認覆蓋+完成偵測+關閉+記錄」一段）目前沒有再複現過，遇到時改用這種拆法即可繞過。

### 錯誤處理

- 「自動化」tab 本身找不到，或 Step 1 讀不到任何群組名稱 → 視為整次執行失敗，記錄後停止，不嘗試處理任何群組。

### 已知限制

- v1 假設「自動化」tab 一畫面可以看完所有群組，不支援捲動。
- Step 1 讀清單（找群組座標、判斷排序）仍然是視覺座標判斷，沒有 UI Automation 可用於精準定位，座標判讀失準會導致該群組失敗（會被記錄並跳過，不影響其他群組）。群組名稱本身已不受此限制 —— Step 2 用 `Open-LineChatWindow` 直接讀視窗標題，不再需要視覺判讀截斷的名稱。

- **Step 2 搜尋框開啟聊天室的做法尚未驗證成功（2026-08-08 設計、2026-08-10 第一次實測失敗）**：貼上的群組名稱沒有進到搜尋框（截圖確認框內仍是空的），原因尚不確定（懷疑清空/貼上時機或點擊座標問題），使用者要求下次加強清空步驟後再試一次（見上方 Step 2 開頭與第 1 步的加強做法）。搜尋結果的排版、比對範圍（是否只比對群組名稱）、結果座標穩不穩定目前都還未知——這些都要等貼上文字本身先確認能穩定生效之後才能驗證。在此之前，每輪仍需保留舊的「截圖判讀清單座標」做法作為並行/備援。
